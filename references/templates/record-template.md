# 记录模板 (Record Template)

> 统一模板，适用于所有类型的记录——经验、知识、创意、参考等，类型通过标签区分。

```markdown
# [标题]

**标签**：#领域标签 #专项标签 #类型标签 #自定义标签
**来源**：[出处 - 实践总结 / 官方文档 / 社区 / 书籍 / URL]
**收录日期**：YYYY-MM-DD
**来源日期**：YYYY-MM-DD（原始内容日期，外部来源必填）
**更新日期**：YYYY-MM-DD（如有更新）
**状态**：✅ 已验证 | ⚠️ 待验证 | 📘 有效 | 🔄 待更新 | 📕 已过时 | ❌ 已废弃 | 🔬 实验性 | 💡 构想中
**可信度**：⭐⭐⭐⭐⭐(官方) ~ ⭐(待验证)
**适用版本**：[技术名称] X.X+（如适用）

### 概要

[一两句话概括核心内容]

### 内容

[主体内容。按可独立阅读的知识博客或技术/学术论文组织，格式随主题选择：
- 经验类：问题/场景 → 根因 → 解决方案及原理 → 验证与边界 → 可复用结论
- 架构类：目标与约束 → 端到端路径 → 组件责任与兼容 → 失败恢复 → 迁移步骤与代价
- 知识类：定义/概念 → 必要前提 → 原理/详解 → 示例 → 适用边界
- 创意类：灵感来源 → 核心想法 → 可行性 → 风险与下一步
- 参考类：用途与适用范围 → 速查表/API 列表/操作手册]

### 关键代码

如无关键代码，可省略本章节，或保留标题并写明“不涉及”。

​```语言
// 代码片段

仅在图片较多（≥5 张）时建议添加。

- [相关记录标题](./other-record.md) - 关联说明

### 验证记录

- [YYYY-MM-DD] 初次记录，来源：[说明]
- [YYYY-MM-DD] 验证/更新说明

## 标签维度参考

> 标签是本系统的核心分类机制。每条记录**至少包含 1 个领域标签 + 1 个类型标签**。

| 维度 | 必选 | 说明 | 预定义标签 |
|------|------|------|-----------|
| **领域** | ✅ ≥1 | 技术/学科大类 | 参见 [tag-registry.md](../tag-registry.md)，维度=domain |
| **类型** | ✅ 1个 | 记录的性质 | 参见 [tag-registry.md](../tag-registry.md)，维度=type |
| **专项** | 可选 | 具体技术/主题 | 参见 [tag-registry.md](../tag-registry.md)，维度=specialty |
| **自定义** | 可选 | 描述性标签 | 可按需创建，但必须在 tag-registry 注册为 custom 并同步 INDEX |

### 标签使用规则

1. **标签格式**：`#小写英文`，多词用连字符 `#behavior-designer`
2. **领域可多选**：如 URP Renderer Feature 同时属于 `#unity` `#shader` `#graphics`
3. **类型单选**：每条记录只能是一种性质
4. **新标签创建**：允许创建细粒度标签，但需**节制**。仅当该概念具有复用价值时才创建，避免标签爆炸。
5. **索引同步**：使用新标签后**必须**同步更新 [INDEX.md](../INDEX.md) 的标签索引，保持闭环。

## 结构约束

- 本模板用于**正式记录**；写入 `data/` 的内容必须完整符合模板要求，不允许用草稿、占位字段或临时段落替代。
- 正式记录的章节标题不得保留模板提示词，例如 `（如有）`、`（如有，...）`；可选性说明应写在标题下方正文中，避免污染 Web 目录和锚点。
- 元数据字段名必须保持稳定，禁止临时改名、插入未注册字段，或为了单条记录例外而改变结构。
- `**状态**` 字段必须严格使用下方“状态定义”中的固定枚举值；补充说明应写入“概要”或“验证记录”，不得写进状态字段本身。
- 若需要修改字段 schema、状态体系、模板章节或其他 Web 解析契约，必须先走 [治理流程](../workflows/governance.md)。

## 读者独立性约束

- 模板字段齐全只代表结构合规，不代表内容可以发布。记录正文必须能被不了解当前对话和项目背景的目标读者独立理解。
- 原创记录应具备知识博客或技术/学术论文的基本论证质量：问题清楚、背景充分、证据可追溯、推理连贯、方法可执行、边界明确、结论收束；不把聊天摘录或内部检查日志直接堆成正文。
- 开头应尽早交代场景、问题、目标与核心结论；不得把关键背景分散到文章末尾或只存在于验证记录。
- 专业术语、内部缩写和实现字段首次出现时应解释其日常含义；示例可以保留具体字段，但正文结论必须先使用通用概念表达。
- 架构、流程和迁移类记录必须说明输入如何经过系统成为用户可观察的输出，不能只列组件名和内部测试项。
- 结尾应按内容类型完成收束，例如操作步骤、采用检查、适用/不适用条件、风险、结论或下一步。
- 相关记录和参考链接用于延伸阅读，不能承担当前正文的必要解释。
- 未声明特殊受众时，默认面向“熟悉该领域日常使用、但未参与当前项目”的读者；不得为了绕过解释责任把受众临时缩窄为项目参与者。
- 新增或实质改写的记录必须通过 [陌生读者冷读门禁](../reviews/README.md)：最终冻结候选须由无历史只读读者明确判定“可发布”；若其后仅有合规机械文本变化，必须以连续继承链连接到最终 SHA。作者自评和结构脚本不能替代。
- 只有不改变语义、Markdown 渲染结构、锚点、链接目标、代码、元数据和读者行动的机械修正，才可由非作者确认精确 diff 后继承既有冷读结论；标题、概要、状态、技术数字、步骤、结论和阅读顺序的变化不属于该豁免。
- 可读性要求按主题复杂度和目标读者成比例执行。简短记录可以保持简短，禁止为了形式统一而制造无用章节、重复解释或冗长清单。

## 状态标记速查

| 标记 | 含义 | 典型场景 |
|------|------|----------|
| ✅ 已验证 | 经实践确认有效 | 踩坑方案、调试结论 |
| ⚠️ 待验证 | 理论可行但未实测 | 新收录的外部方案 |
| 📘 有效 | 信息准确且当前适用 | 概念原理、API 文档 |
| 🔄 待更新 | 有新版本或变更 | 版本已更新的知识 |
| 📕 已过时 | 不再适用当前环境 | 旧版本 API |
| ❌ 已废弃 | 错误或有风险 | 证伪的方案 |
| 🔬 实验性 | 非主流/试探性方案 | 创新尝试 |
| 💡 构想中 | 创意/灵感阶段 | 产品创意、技术设想 |

## 状态定义

> 此表由 Web 渲染管线自动解析，驱动状态图标渲染与颜色分类。
> **重要**：记录中的状态 Emoji 必须与本表完全一致（精确到 Unicode 码点），不可使用近似或外观相似的 Emoji。

| Emoji | 标签 | 颜色 | SVG | 场景 |
|-------|------|------|-----|------|
| ✅ | 已验证 | success | status-verified | 踩坑方案、调试结论 |
| ⚠️ | 待验证 | warning | status-pending | 新收录的外部方案 |
| 📘 | 有效 | info | status-valid | 概念原理、API 文档 |
| 🔄 | 待更新 | warning | status-update | 版本已更新的知识 |
| 📕 | 已过时 | danger | status-obsolete | 旧版本 API |
| ❌ | 已废弃 | danger | status-deprecated | 证伪的方案 |
| 🔬 | 实验性 | info | status-experimental | 创新尝试 |
| 💡 | 构想中 | info | status-concept | 灵感阶段 |
