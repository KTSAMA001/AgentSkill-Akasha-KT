# 记录流程

> 将有价值的内容保存为独立记录文件

---

## 一、流程总览

1. 🔴 **CRITICAL - 同步仓库**：`git pull origin main`
2. 🟡 **IMPORTANT - 确定文件名**：`kebab-case` 自解释命名
3. 🟡 **IMPORTANT - 判断记录类型**：原创整理 **or** 学习用途本地留档（见下方「二、记录类型分支」）
4. 🔴 **CRITICAL - 全面验证**：按 [validate.md](./validate.md) 检查（重复检测、正确性、时效性、敏感信息与脱敏审查等）
5. 🔴 **CRITICAL - 记录前预览与脱敏说明**：向用户说明拟记录内容、是否发现敏感信息、发现的类型或位置概览、拟采用的脱敏方式；发现敏感信息时必须先脱敏再写入
6. 🔴 **CRITICAL - 格式化写入正式候选**：按对应类型的写入规范写入 `data/` 目录；候选必须内容完整，不得使用占位符或半结构草稿
7. 🟡 **IMPORTANT - 打标签**：确保至少 1 个领域标签 + 1 个类型标签
8. 🟡 **IMPORTANT - 保存资源**：先保存候选正文直接引用的图片等资源，再按资源文件规范使用相对路径引用
9. 🔴 **CRITICAL - 冻结候选并完成陌生读者冷读**：按下方门禁隔离审查；最终候选必须直接获得“可发布”，或具有从最近“可发布”候选连续连接到最终 SHA-256 的机械继承证据
10. 🔴 **CRITICAL - 更新索引**：更新 [INDEX.md](../INDEX.md) 的文件清单（如有新标签则同步更新 tag-registry.md（如新标签））
11. 🔴 **CRITICAL - 提交推送**：Git Commit & Push

### 正式记录原则

- 写入 `data/` 的内容必须一次成型为正式记录，禁止写入草稿、占位符、临时片段或“后续再整理”的半结构化内容。
- 记录流程只负责内容入库与索引同步，不负责修改模板、workflow、字段 schema、索引规则等系统层契约；此类变更必须走 [governance.md](./governance.md)。
- 若当前信息不足以形成正式记录，应先继续整理信息或等待补充，不得通过降低结构要求来完成入库。
- 记录前预览是正式写入的前置门禁；预览必须覆盖脱敏审查结果，且不得直接暴露完整敏感值。

### 记录前预览与脱敏门禁

- 预览必须先于写入 `data/`，并包含：拟记录标题/概要、记录类型、主要信息来源、脱敏审查结果、拟写入位置。
- 外部公开资料离线保存类任务的用户可见记录类型统一写作“学习用途本地留档”或“离线留档”。
- 脱敏审查结果必须说明是否发现敏感信息；若发现，只说明类型或位置概览与处理方式，不复述完整敏感值。
- 常见敏感信息包括真实项目名、内部仓库/分支/目录结构、本机绝对路径、账号、邮箱、手机号、token、API key、密码、私钥、凭据文件内容、客户/人员信息、未公开业务上下文、可反推出内部资产的资源名或标识符。
- 发现敏感信息时，必须先泛化、替换为占位符、删除或改写为可复用技术结论，再进入正式写入；用户要求保留敏感信息时，不得写入共享阿卡西数据层。
- 脱敏审查以语义判断为主；脚本或固定模式扫描只能作为辅助告警，不能作为“无敏感信息”的证明。

### 陌生读者冷读门禁

> 目标不是把每篇记录写成长文，而是确保目标读者不依赖当前对话、作者记忆或项目参与经历，也能理解这条记录为何存在、核心结论是什么、怎样使用以及边界在哪里。

#### 哪些变化必须审查

- 新增正式记录；
- 标题、概要、状态、正文结构、技术数字、代码、步骤、方案、因果链、适用范围或结论发生实质变化；
- 架构、排障、迁移、研究综合等依赖背景较多的记录。

只有同时满足“不改变正文语义、Markdown 渲染结构、目录锚点、链接目标、代码、元数据和读者行动”的变化，才可按机械修正处理，例如不参与 Markdown 语法的空白、正文普通文字中的标点、无歧义错字或自动生成索引。`#`、反引号、列表符、链接括号等 Markdown 定界符即使只改一个字符，也不能默认视为机械修正。日期、标签、来源目标、标题、概要、状态、技术数字、代码、步骤、结论、章节顺序或“已验证/已审阅”声明发生变化时，不得豁免完整冷读。

学习用途本地留档不得按冷读意见改写外部原文；冷读只审核本地概要、元数据、导航、资源完整性和适用说明。若原文自身依赖外部背景，应在本地说明中标注，而不是篡改原文。

#### 隔离读者与输入白名单

- 必须新建一个**不继承父任务对话或历史的新上下文**（例如创建子 Agent 时使用无历史分叉），而不是让已经参与实现的 Agent 在提示中“假装不知道”。
- 读者只能只读访问：冻结的目标记录、正文直接引用的 `assets/<record-name>/` 资源、目标读者画像和审核问题；不得提供实现聊天、作者解释、预期答案或未写进正文的项目资料，也不得允许读者修改文件或执行 Git 写操作。
- 若记录没有声明特殊受众，默认读者是“熟悉该领域日常使用、但未参与当前项目，也不知道当前对话和内部术语的普通实践者”。更窄的受众必须在记录中明示并说明理由，不能为了通过审核临时把读者定义成项目参与者。
- 无法获得无历史只读读者时，门禁状态只能是“无法判断”；作者自审可以帮助修改，但不能代替独立冷读，也不能把新增或实质改写的候选作为已通过记录提交。

#### 冻结候选与审核证据

1. 在委派前计算目标记录的完整 SHA-256，并为正文直接引用的资源生成“相对路径 + SHA-256”清单，把这些摘要交给读者核对；读者必须在阅读前和给出结论前各自重算一次。读者返回结论前，作者不得修改目标记录或资源；起止摘要不一致会使本轮结论失效。
2. 审核证据保存到 `references/reviews/<record-name>/<YYYY-MM-DD>-<sha256前12位>.md`，格式遵循 [reviews/README.md](../reviews/README.md)。证据必须记录审核任务或上下文 ID、无历史上下文的创建方式、目标、完整审核提示、实际输入白名单、候选与资源的起止 SHA-256、日期、目标读者画像，以及读者未经删改的完整原始输出；缺少任一项时结论只能是“无法判断”。
3. 证据文件不得包含凭据、真实内部路径或其他不应进入仓库的信息；必要时应先让读者使用仓库相对位置和泛化标识。
4. 保存证据后、提交前，发布执行者必须再次重算记录与**正文直接引用资源的完整路径集合及摘要**，把复算时间和结果写入证据并逐项核对。最终 SHA 与“可发布”证据不一致时，必须重新冷读；唯一例外是下一条规定的机械继承证据。
5. 审核后发生机械修正时，必须把旧/新完整记录 SHA-256、两端完全相同的直接引用资源路径与摘要清单、精确文本 diff、渲染与链接核对结果、非作者复核者的任务/上下文 ID 和逐字结论保存为同目录下的 `<YYYY-MM-DD>-<新记录sha前12位>-mechanical.md`。任何资源路径或内容摘要发生变化，都必须重新完整冷读，不能走机械继承。只有非作者独立重算并明确判定“可继承”时，新记录 SHA 才能沿用上一份“可发布”证据；否则重新完整冷读。一次继承只跨一个明确 diff，不得用笼统声明覆盖多轮修改。保存机械证据后，发布者还必须复算最终记录和资源清单并写入该证据；不匹配则重新审核。

#### 冷读输出至少包含

1. **读者复述**：不参考作者意图，用自己的话复述文章主旨和运行机制，用于暴露理解偏差。
2. **阻断问题**：标出缺失背景、未解释术语、跳跃因果、依赖内部上下文、虎头蛇尾或无法执行的部分，尽量引用精确位置。
3. **结构建议**：说明需要补充、删减、前移或下沉的内容。
4. **明确结论**：只能给出“可发布”“修改后发布”或“无法判断”。后两者都是阻断状态；不得用结构脚本通过代替可读性判断。

#### 正文最低可理解性要求

- 开头说明适用场景、真实问题、目标结果和核心结论；
- 专业术语在第一次出现时用目标读者能懂的日常语言解释；
- 架构或流程记录必须给出端到端路径，说明输入怎样变成用户可观察的输出；
- 关键依赖、兼容关系、失败方式、取舍与证据边界不能只靠作者脑补；
- 结尾必须收束为可执行步骤、采用检查、适用/不适用边界或明确结论，不能停在零散测试数字；
- “相关记录”只能用于扩展阅读，正文不能依赖读者打开其他记录后才成立；
- 长度和解释深度按目标读者与主题复杂度调整，禁止为了满足门禁机械堆砌术语表和清单。

只有与**最终候选完整 SHA-256** 绑定的“可发布”，或从最近一份“可发布”证据逐步连接到最终 SHA 的完整机械继承链，才能通过门禁。收到“修改后发布”后，作者必须修复阻断项；修订会产生新摘要，必须再次把最终候选交给无历史只读读者，直到获得“可发布”。发布阻断项不能由作者写一句异议后豁免；只有非阻断建议可以保留，并须在审核证据中记录理由。结构再次大改时必须重新执行完整冷读，不能只核对改动清单。

### 强制脚本辅助

- 全库结构校验**必须**使用 [validate_records.py](../scripts/validate_records.py) 做只读检查，禁止跳过脚本直接凭人工目测宣称“已验证”。
- 文件清单同步**必须**使用 [regenerate_index.py](../scripts/regenerate_index.py) 重建 `INDEX.md` 的“文件清单”表格，禁止手工逐行维护派生表格。
- 脚本用法与边界**必须**遵循 [scripts/README.md](../scripts/README.md)。

### 强制执行顺序

```bash
python3 references/scripts/validate_records.py
python3 references/scripts/regenerate_index.py
python3 references/scripts/validate_records.py
```

- 第一次校验用于发现结构问题；未执行不得进入后续索引同步步骤。
- 索引重建只负责同步 `INDEX.md` 文件清单，不修正文义问题；禁止把脚本输出误解为“记录内容已经合规”。
- 第二次校验用于确认索引已同步，且没有引入新的结构错误；未完成第二次校验，不得宣称记录流程已闭环完成。

## 二、记录类型分支

收到记录请求时，首先判断内容类型并选择对应流程：

### 判断规则

| 条件 | 记录类型 | 写入规范 |
|------|----------|----------|
| 用户要求「学习留档」「本地留档」「离线保存」「原文保存」「避免网络问题导致无法查看」| **学习用途本地留档** | 见 [二-B 学习用途本地留档流程](#二-b-学习用途本地留档流程) |
| 内容来自外部公开文章，且需要为学习、研究或离线查看完整保留 | **学习用途本地留档** | 见 [二-B 学习用途本地留档流程](#二-b-学习用途本地留档流程) |
| 用户自己的经验/知识/创意 | **原创整理** | 见 [三、提取要点清单](#三提取要点清单)，按模板整理 |
| 来自讨论但需要结构化提炼 | **原创整理** | 按模板整理，提炼要点 |

### 🔴 二-B 学习用途本地留档流程

> 当用户要求为学习、研究或避免网络问题导致无法查看，将外部公开文章（知乎、博客、论坛等）离线保存到本地知识库时使用。

**核心原则：为离线学习保留公开原文，不改写。**

1. **抓取完整内容**
   - 优先使用 `opencli-rs` 对应站点的 `download` 命令
   - 若 opencli-rs 截断，使用 Chrome AppleScript JS 提取（需用户开启「允许 Apple 事件中的 JavaScript」）
   - 提取 HTML 或纯文本均可，但**必须确保内容完整**，不能截断

2. **下载图片到本地**
   - 从文章中提取所有内容相关图片 URL（排除头像、广告、装饰图）
   - 下载到 `assets/<record-name>/` 目录
   - 命名规则：`序号-描述.扩展名`（如 `01-article-cover.jpg`）
   - 下载时设置 `Referer` 和 `User-Agent` 请求头避免防盗链

3. **写入记录（格式要求）**
   - **元数据块**：使用标准模板（标签、来源、收录日期等）
   - **概要**：1-2 句话概括文章主题（可自行撰写）
   - **内容**：`### 内容` 标题下**完整保留原文**，包括：
     - 原文的标题层级结构（h2、h3 等）
     - 原文的段落文字（不删改、不缩写）
     - 原文的表格（按 Markdown 表格格式还原）
     - 原文的代码块（按对应语言标记还原）
     - 原文的引用块（blockquote）
   - **图片替换**：将原文图片 URL 替换为本地相对路径 `![](../assets/<record-name>/xx.jpg)`
   - **禁止**：
     - ❌ 改写、缩写、概括原文内容
     - ❌ 调整原文结构或顺序
     - ❌ 添加自己的分析或注释（如有补充，放在「### 内容」之外）
     - ❌ 省略任何段落或章节（即使是「不重要的」部分）

4. **参考链接与相关记录**
   - 在 `### 参考链接` 中记录原文 URL
   - 在 `### 相关记录` 中关联相关的阿卡西记录

**格式示例**：

```markdown
# 文章标题

**标签**：#领域标签 #类型标签
**来源**：[来源平台 - 作者名](URL)
**收录日期**：YYYY-MM-DD
**来源日期**：原文发布日期
**状态**：⚠️ 待验证
**可信度**：⭐⭐⭐（说明）

### 概要

一两句话概括文章主题。

### 内容

![封面图](../assets/record-name/01-cover.jpg)

原文内容完整保留在这里，包括标题、段落、表格、代码块、图片引用……

## 原文二级标题

原文段落内容……

![配图](../assets/record-name/02-screenshot.png)

### 参考链接

- [原文标题](URL) - 原文

### 相关记录

- [相关记录](./other-record.md) - 关联说明

### 验证记录

- [YYYY-MM-DD] 初次记录，来源：[说明]
```

**已有参考**：[endfield-rendering-study.md](../../data/endfield-rendering-study.md)、[modified-renderdoc-wuwa-capture.md](../../data/modified-renderdoc-wuwa-capture.md) 是学习用途本地留档的标准范例。

## 二、文件命名规则

- 格式：`kebab-case`，全小写，连字符分隔
- 要求：自解释，无需依赖目录上下文即可理解内容
- 位置：一律写入 `data/*.md`，**不创建子目录**

### 命名示例
| 内容 | 文件名 |
|------|--------|
| URP 自定义 Renderer Feature | `urp-renderer-feature-custom.md` |
| C# 异步编程踩坑 | `csharp-async-pitfalls.md` |
| Git PAT 认证故障 | `git-pat-credential-fix.md` |
| 明日方舟工业风 UI 分析 | `arknights-ui-industrial-style.md` |
| 3D 美少女智能家具创意 | `idea-3d-girl-smart-furniture.md` |

## 三、标签打标

> 标签是唯一的分类机制，务必认真打标。

### 要求
- 每条记录 **至少 2 个标签**
- 查看 [tag-registry.md](../tag-registry.md)，**优先复用已有标签**
- **创建原则**：允许细粒度标签，但需**节制**。仅当某概念具有**复用价值**（预计会有多条记录归属此类）时才创建新标签。对于极低频或一次性的细节概念，依赖全文检索即可。
- 新标签格式：`#小写英文`，多词用连字符：`#behavior-designer`
- 如使用了新标签，**必须**同步更新 [tag-registry.md](../tag-registry.md) 与 [INDEX.md](../INDEX.md) 的相关内容。

### 示例
| 内容 | 标签 |
|------|------|
| URP Renderer Feature 开发经验 | `#unity` `#shader` `#urp` `#renderer-feature` `#experience` |
| PBR 渲染理论 | `#graphics` `#pbr` `#brdf` `#knowledge` |
| Git PAT 认证故障 | `#git` `#credential` `#experience` `#bug` |
| 3D 智能家具创意 | `#idea` `#smart-furniture` |

## 四、提取要点清单

根据内容性质，关注以下要点：

### 经验类 (#experience)
- **标题**：一句话概括问题与方案
- **问题描述**：发生的场景、报错信息
- **解决方案**：具体的修复步骤或代码
- **版本环境**：Unity 202x, VS Code xxx
- **参考链接**：StackOverflow, Unity Forum

### 知识类 (#knowledge)
- **标题**：知识点名称
- **定义**：简练的概念解释
- **原理**：底层逻辑或工作机制
- **来源**：官方文档、权威书籍
- **示例**：简单的用法演示

### 创意类 (#idea)
- **标题**：创意名称
- **灵感来源**：触发想法的事件/需求
- **核心想法**：创意的完整描述
- **可行性**：初步评估

## 五、资源文件处理

> 当记录包含图片、示意图等需要离线保存的资源时，按以下规范处理。

### 适用场景

- 抓取外部文章（知乎、CSDN 等）中的配图
- 技术示意图、架构图、流程图
- UI 截图、效果对比图
- 任何需要离线保存以防链接失效的图片资源

### 存储规范

| 项目 | 规则 |
|------|------|
| **存储位置** | `assets/<record-name>/`（record-name 为记录文件名去掉 `.md`） |
| **文件命名** | `序号-描述.扩展名`，如 `01-retarget-concept.png`、`03-architecture-diagram.png` |
| **序号规则** | 两位数字，按内容出现顺序编号：`01-`、`02-`、`03-` ... |
| **描述规则** | `kebab-case`，简明描述图片内容 |
| **支持格式** | `.png`、`.jpg`、`.gif`、`.svg`、`.webp` |

### 引用方式

在 md 文件中使用**相对路径**引用，**禁止使用绝对路径**：

```markdown
![图片描述 - 补充说明](../assets/<record-name>/01-image-name.png)
```

- `data/xxx.md` → `../assets/xxx/` （上一级再进入 assets）
- alt 文本应包含图片内容描述，便于无图阅读

### 图片资源清单（可选）

当图片较多（≥5 张）时，建议在记录末尾添加资源清单表格：

```markdown
### 图片资源清单

| # | 文件名 | 说明 | 大小 |
|---|--------|------|------|
| 1 | `01-xxx.png` | 描述 | XX KB |
```

### 注意事项

- **不保存**：用户头像、广告图、网站 UI 装饰等非内容图片
- **不保存**：可通过代码/文字精确描述的简单信息
- **需保存**：技术示意图、架构图、效果对比图等对理解内容有重要价值的图片
- 下载图片时需设置合适的 `Referer` 和 `User-Agent` 请求头以避免防盗链

## 六、索引更新

每次新增/修改记录后，**必须**同步更新 [INDEX.md](../INDEX.md)：

1. **文件清单**：在表格中添加一行，填入文件名、标签、状态、简述
2. **标签概览**：仅当使用了新标签时，将新标签添加到 [tag-registry.md](../tag-registry.md)（含维度和说明）
3. **一致性原则**：索引层仅做派生性同步，不得在更新索引时私自改写记录正文含义或新增未走治理流程的结构字段

## 七、仓库同步与规范

### Commit 规范
`git commit -m "Type: Subject"`

| 类型 | 格式示例 |
|------|----------|
| **新增记录** | `docs: add [文件名]` |
| **更新内容** | `docs: update [文件名] - [说明]` |
| **修正错误** | `fix: correct [文件名] - [错误]` |
| **系统维护** | `chore: [说明]` |

### 冲突解决
```bash
git pull --rebase origin main
# 解决冲突
git add . && git rebase --continue
git push origin main
```
