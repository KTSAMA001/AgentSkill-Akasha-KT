# 验证与修正流程

> 核验已有 `data/*.md` 记录；正确则保留，错误、过时或不完整时按证据修正。本流程不修改系统规则，相关需求转 [governance.md](./governance.md)。

## 1. 范围与触发

验证可以由以下情况触发：

- 引用记录回答问题时需要确认适用性；
- 用户指出“不对”“过时”或提供新的实践结果；
- 技术版本、规范或官方来源发生变化；
- 多条记录互相矛盾；
- 新记录写入前需要重复、正确性和时效性检查；
- 需要检查结构、资源、索引、脱敏或陌生读者可读性。

允许修改目标 `data/*.md`、其直接资源、对应冷读证据、`INDEX.md`，以及确有新标签时的 `tag-registry.md`。不得借验证流程改模板、workflow、schema、状态体系或其他 Web 契约，也不得扩大到无关记录。

## 2. 验证维度

| 维度 | 要回答的问题 |
|---|---|
| 正确性 | 结论、代码、数字和因果是否有证据支持，实践是否可复现 |
| 时效性 | 版本、API、平台或环境变化是否改变结论 |
| 来源性 | 来源是否一手、可靠、可追溯，是否已有更新 |
| 完整性 | 元数据、标签、必要章节、步骤和结论是否齐全 |
| 资源完整性 | 正文引用的资源是否存在、可读且属于目标记录 |
| 结构一致性 | 文件名、字段、状态、相对路径和 INDEX 是否符合契约 |
| 脱敏 | 是否泄露内部路径、账号、凭据、人员/客户或未公开上下文 |
| 读者独立性 | 不知道当前对话和项目背景的目标读者能否理解问题、机制、证据、边界和行动 |

机器检查只覆盖部分结构问题。脚本退出码不能证明事实正确、信息最新、敏感信息已经清除或文章可以独立理解。

## 3. 执行步骤

1. **确认授权和目标**：明确要核验的记录、问题类型和可修改范围。仅检查时不得擅自修正。
2. **准备当前版本**：若本次包括发布，在修改前检查仓库、分支、远端和工作树，并按授权安全同步；冲突或分叉时停止，不自动改写历史。
3. **定位记录**：仅在 `data/*.md` 中检索并完整读取目标记录，同时读取其直接资源和必要来源。
4. **建立证据**：核对版本、官方或一手来源、实践结果和相关记录；明确事实、推断、未知及冲突证据。
5. **决定处理**：记录正确则不改正文；需修正时采用下节策略，并更新“更新日期”“状态”和“验证记录”。
6. **语义复核**：重新检查脱敏、可读性、适用边界和相关记录影响。实质改写按 [reviews/README.md](../reviews/README.md) 对最终候选重新冷读。
7. **机器检查与索引**：按 [scripts/README.md](../scripts/README.md) 执行“校验 → 重建 INDEX 文件清单 → 再校验”；新标签同步注册。
8. **发布与报告**：只在授权范围内精确暂存、提交和推送本次文件；报告证据、改动、验证范围、未验证边界及真实发布结果。

## 4. 修正策略

### 记录仍然正确

- 没有新证据需要改变正文、状态或验证记录时，保持零内容改动。
- 向用户说明核对了什么、证据支持到何种程度，以及仍未验证的边界。

### 小幅补充

补充版本限制、来源或注意事项，同时更新日期和验证记录。例如：

```markdown
### 验证记录

- [YYYY-MM-DD] 修正：在 Unity 2022+ 还需要配置 xxx；依据：[来源或验证]
```

只要改动影响语义、元数据、链接、代码、读者行动或 Markdown 结构，就不是可免审的机械修正，必须重新完整冷读。

### 重大修正或废弃

- 在正文中给出当前正确方案、证据和迁移说明。
- 历史方案仍有理解价值时可折叠保留，并明确旧版本边界；错误或有风险的方案不得继续作为默认建议。
- 状态改为对应固定枚举，如 `🔄 待更新`、`📕 已过时` 或 `❌ 已废弃`，说明替代方案和影响范围。
- 重新执行完整冷读，不能继承旧候选结论。

示例：

```markdown
<details>
<summary>历史方案（已废弃）</summary>

[旧方案及原适用版本]

</details>
```

## 5. 冲突与交叉验证

| 冲突类型 | 处理 |
|---|---|
| 场景差异 | 保留两条结论，分别说明前提和适用场景，并相互链接 |
| 版本差异 | 保留历史结论及版本边界，给出当前版本建议 |
| 事实冲突 | 追查一手证据或最小复现；保留证据支持的结论，修正或废弃错误结论 |
| 证据不足 | 不强行合并，标记待验证并列出缺失证据 |

相关记录使用 `./other-record.md`。它们可以互相佐证，但每篇正文仍须独立成立。

## 6. 脱敏与陌生读者复审

- 语义检查覆盖正文、代码、路径、命令输出、资源名和链接；固定模式扫描只能发现它已覆盖的高危形式。
- 向用户报告敏感问题时只说明类型、位置概览和处理方式，不回显完整秘密。
- 新增内容或实质改写必须使用不继承当前对话的新只读读者；作者自评和参与修改的 Agent 不能代替。
- 冷读必须绑定最终记录和直接资源的完整 SHA-256，保存完整提示、白名单、上下文 ID、起止重算和未经删改的原始输出。
- 只有“可发布”通过；“修改后发布”和“无法判断”均阻断。完整格式和机械继承边界以 [reviews/README.md](../reviews/README.md) 为唯一权威。

## 7. 结构、索引与 Git

```bash
python3 references/scripts/validate_records.py
python3 references/scripts/regenerate_index.py
python3 references/scripts/validate_records.py
```

- 首轮除本次修改造成的预期 INDEX 差异外还有错误时，先修复；不得忽略非零结果。
- 生成器只维护 INDEX 文件清单，不反向修改正文，也不替代标签概览治理。
- 标签或状态变化会影响索引；新增标签还须更新 `tag-registry.md`。
- 若获得 Git 发布授权，只暂存目标记录、对应资源、审核证据、索引和必要标签文件；禁止用宽泛暂存夹带无关改动。
- 推送失败时只能报告本地实际状态，不能声称远端已更新。

## 完成检查

- [ ] 已明确验证类型、目标记录、授权范围和适用版本。
- [ ] 结论由当前证据支持，并显式保留冲突与未知。
- [ ] 无需修正时保持零正文改动；需要修正时已更新日期、状态和验证记录。
- [ ] 没有借验证流程修改系统层规则或无关记录。
- [ ] 脱敏、资源、结构和陌生读者可读性均按适用门禁检查。
- [ ] 实质改写的最终候选已有匹配摘要的“可发布”证据。
- [ ] 已完成“校验 → 索引生成 → 再校验”，并处理标签变化。
- [ ] Git 动作只在授权范围内执行，最终报告与真实本地/远端状态一致。
