### 完整复述

文章绑定公开仓库的固定提交 `5b9852d71e53527526c695e9c25e72739bfa7eb6`，注明来源 Unity `2022.3.17f1c1`、URP `14.0.9`，并把源码静态核对、项目 D3D11 配置、Unity 官方投影约定和未运行边界分开陈述。

主链为：

1. CPU 合并地形 Mesh，逐三角形按 `ceil(max(1, densityPerArea × area))` 生成草实例，因此每个三角形至少一株，草量不仅取决于面积，也取决于三角化密度，退化三角形也可能贡献实例。
2. 每株实例上传一个 `64 B` TRS；每帧清零 Append 计数，Compute Shader 遍历实例并追加通过筛选的完整 TRS。
3. `[numthreads(640,1,1)]` 配合 `1 + floor(count/640)`；非整倍数时等于向上取整，整倍数时多一组，但线程入口的范围检查避免越界。
4. `CopyCount(result, args, sizeof(uint))` 将 Append 计数写入五字段间接参数的第二项，即实例数。
5. `DrawMeshInstancedIndirect` 使用筛选后矩阵绘制；固定的 `1000³` 总 Bounds 决定整批 Draw 是否先被 Unity 拒绝，过小会整批消失，过大则损失 CPU 粗剔除收益，且无法追回已经执行的 Compute 成本。

投影部分明确区分：

- 源码上传原始 `Camera.projectionMatrix × worldToCameraMatrix`，没有调用 `GL.GetGPUProjectionMatrix`。
- 对普通透视、相机前方且 `w > 0` 的点，原始 Unity/OpenGL-like 矩阵合法深度为 `-w <= z <= w`，所以 `abs(z) <= abs(w)`确实同时覆盖近、远边界。
- 如果换成 D3D11 等后端调整后的 GPU 投影矩阵，合法深度是 `0 <= z <= w`；绝对值会丢失 `z >= 0` 下界并接受部分负 z。
- 文章没有把这一结论外推至自定义、斜截面、XR 等投影。

剔除错误说明完整：外层循环虽执行六次，但循环索引未参与计算，实际只是六次重复同一组裁剪盒条件；“至少一个 AABB 角点进入盒内”不是保守包围体–视锥相交测试，大包围体可能与视锥相交而八角都在外侧。`1.1/1.5` 放宽系数不能修复算法，裁剪坐标噪声和 `w` 距离混用会受相机投影影响，固定局部包围体也未由真实 Mesh 和顶点动画位移推导。

CPU oracle 方案给出了可执行主路径：固定 TRS 输入，以原始 `id.x` 追加调试索引，异步读回集合；CPU 用独立六平面、八角点规则生成 `T`，GPU 生成 `G`；保守粗筛要求 `T ⊆ G`，若要完整复现含距离规则的参考谓词则要求 `G = T`。测试范围包括擦边、大盒包围视锥、相机位于盒内、不同 FOV 和近远面。

最后提出的改造顺序也闭环：固定投影约定、上传六平面或实现经验证的齐次保守测试、构造覆盖旋转缩放和动画的包围体、按平面整体拒绝、将世界空间距离规则与视锥分离、推导或分区 Draw Bounds、通过 CPU/GPU 原始索引集合证明无漏项后再测性能。
