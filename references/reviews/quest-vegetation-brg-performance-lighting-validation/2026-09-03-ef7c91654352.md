2) 完整复述

这篇文章研究的是 2026-08-19 在 Quest 3S 上留下的四组历史 A/B/A 窗口：先运行 BRG 植被系统，再切换为普通 GameObject 系统，最后切回 BRG。它比较的不是单纯 Draw API，而是两套完整运行路径：BRG 使用批量实例组织，并预先把 Bakery L2 探针求成逐株最终 RGB；GO 路径展开 GameObject、Transform、MeshRenderer、LODGroup，使用 GPU Instancing 和 BlendProbes，并在 Shader 中消费另一种 SH 表达。因此两侧的对象生命周期、光照表达和运行成本并不严格等价。

四组工作量分别是：

- 稀疏真实草：8192 株分布在约 504×504 米的名义网格中。设备采样时的姿态、质量档和实际可见数没有保存；编辑器默认姿态下的 520 株可见不能代替设备数据。
- 高密度真实草：8192 株全部可见，单株 640 顶点、704 三角形，约 576.7 万实例三角形；草使用 Alpha Clip、双面渲染，并覆盖较大屏幕区域。相机、场地、FOV、Eye Buffer、刷新率、Heap、LOD 和光照条件均有说明。
- 大尺寸 Box：仍为 8192 个实例，但单体只有 24 顶点、12 三角形，并保持真实草的外形尺度；“全部入画”来自头显观察和截图，不是程序化计数。
- 15% Box：同样是 24 顶点、12 三角形，缩小到原尺寸的 15%，静态水平包络不相交，但这一判断不包含 Shader 顶点位移；全部入画仍是人工观察证据。

采样约每秒一次、每段约 15–20 秒，表中只有窗口汇总值，没有逐样本序列，也不知道窗口聚合公式。因此不能计算方差、置信区间或显著性。`CPU+GPU ms`、`CPU %`、`GPU %` 的精确定义和归一化方式已经丢失，只能按原字段描述；`Stale/s` 被解释为合成器复用旧帧的频率；PSS 是整个应用进程的比例分摊内存，不是植被独占显存或托管堆。

直接结果是：稀疏真实草三段都约 90 FPS；高密度真实草三段都约 20 FPS，历史 `GPU %` 约 99%，并伴随约 72 Stale/s；大 Box 为约 83/72/85 FPS；15% Box 为约 90.5/81.5/90.6 FPS。两个 Box 组中，GO 段的 `CPU %`、`CPU+GPU ms`、Stale 和 PSS 相对两侧 BRG 窗口明显上升，回切后性能相关字段恢复。不过，15% Box 的 GO 段同时获得了更高 GPU 档位和时钟。

文章据此只提出有限解释：Box 组的现象与 GO 完整对象路径产生更高 CPU 侧总压力一致；高密度真实草的低帧率与高 `GPU %` 组合，与 GPU 饱和以及几何和覆盖成本主导一致；BRG 可以改变提交和对象组织，但不会自动消除已经可见的顶点、三角形、双面栅格化、Alpha Clip 和 Overdraw。因为没有 GO 侧可比的提交命令计数，BRG 侧一个 `BatchDrawCommand` 不能证明 BRG 减少了 Draw Call 或提交命令。PSS 差异也不能全部归因于 GameObject，更不能据回切残留断言内存泄漏。

会话证据并不统一：只有 15% Box 保存了三段同一 PID；高密度草和大 Box只有连续应用会话说明；稀疏组只有顺序窗口与操作者切换说明；四组都没有自动模式切换事件日志。不同几何还来自不同 APK，大 Box 与 15% Box 的包体积相差 31.111%，且原因不明。因此包内 A/B/A 可以作为受限的回切观察，跨 APK 的草、Box、缩小 Box 比较只能支持相关性，不能称为单变量因果证明。

历史 APK 还使用旧逐株光照协议，不能验证当前 32 B ABI、Shader、运行时组织或 Quest Vulkan 性能。文末给出的升级协议要求在同一 APK、同一进程和冻结工作量下自动切换，保存构建与会话标识、温度、时钟、可见工作量和原始逐样本，区分“完整系统比较”与“只比较提交路径”，平衡执行顺序并跨会话重复。相关链接只用于扩展当前架构与光照协议，并非理解本文历史结论的必要前提。
