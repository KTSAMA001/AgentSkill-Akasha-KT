2. 自己的话完整复述

文章要解决的不是“怎样把植物放到鼠标位置”，而是如何让一次植被编辑在五类状态间保持可解释：尚未确认的临时操作、权威作者数据、由作者数据生成的缓存、磁盘文件，以及编辑器里正在显示的 BRG 结果。看见变化、能够 Undo、已经写盘和渲染已刷新是不同事实。

工具有两条彼此独立的输出路径：

- BRG 路径要求先确定一个 Cell。Cell 是场景里的管理器及其绑定 SceneAsset 所代表的区域；SceneAsset 保存 Prototype 表、Heap 和逐株作者实例，是权威数据，Heap 只是 Cell 内的空间分桶。Paint、Erase、Replace、Reproject、Select/Edit 都先操作 Heap 副本、目标 StableGuid 集合或临时矩阵。取消时丢弃暂存；鼠标抬起或点击显式应用时，先为 SceneAsset 建立 Undo 边界，再写回作者数据，同步校验和编译受影响 Heap，重新合成整份资产的编译哈希，调用保存 API，发送进程内变更通知，最后由编辑器 BRG 宿主按更宽的内容指纹重建显示。当前这是一条同步调用链，但“保存 API 已调用”并不证明磁盘内容已成功更新。
- GameObject 路径只支持 Paint/Erase。拖动期间就直接在命中表面所属普通 Scene 中创建 Prefab 实例或删除专用根下的对象，但整笔变化都登记进一个 Unity Undo Group。鼠标抬起只是确认并折叠该组；Escape、窗口关闭或未完成对象释放会回滚整笔。它只把 Scene 标记为 Dirty，不自动保存 Scene，也不进入 BRG 的 Commit、Compile 或通知链。

表面和多 Scene 规则也能独立还原：用户要显式选定一个表面，一笔开始后锁定该表面，移到另一网格不会自动换面。MeshRenderer 路径不要求 Collider 或 Read/Write；Terrain 精确命中需要 TerrainCollider。BRG 表面必须和当前 Cell 位于同一已加载 Scene；Cell 可以处于非 Active 的 Additive Scene。GameObject 可以面向任意已加载的普通 Scene，结果归属命中表面的 Scene，但当前“允许选表面”和“真正写入时拒绝 Preview Scene”是两个尚未统一的门禁。底层 GameObject 服务具备在同一 Undo Group 中分别写入多个 Scene 的原语，但 Painter UI 实际仍是一笔锁定一面，不能宣传成跨 Scene 连续拖刷。

BRG Undo/Redo 被拆成三层语义：

- 内存与显示：完整对象 Undo 恢复序列化 SceneAsset，BRG 宿主收到 Unity Undo/Redo 事件后强制重建；文章只静态确认了这条机制，没有运行结果证明作者数据、缓存和画面逐项一致。
- 显式保存后重载：Undo 或 Redo 后需要用户再次明确保存，再重导入或重启验证对应版本；当前 Undo/Redo 回调不会自动编译、保存或发送通知，这层尚未验证。
- 未保存关闭：必须让用户理解是在保存还是放弃，或明确回到上一磁盘版本；模块当前没有自己的关闭提示与恢复协议，也未证明 Unity 宿主会怎样提示 ScriptableObject 资产。

文章还给出了 A/B 对称实验，避免初次操作的自动保存掩盖 Redo 未持久化。GameObject 则依赖整笔 Undo Group 和标准 Scene Dirty/保存边界，现有测试定义不等于已经运行，也没有证明 Scene 已写盘。

失败恢复方面，当前 Stage 在正常取消时不会碰权威数据，Commit 写回前会检查身份、有限 Transform 和 Heap 归属，显式批量应用有外层 Undo 回退。但 Paint/Erase 在作者数据写回后直接编译，没有同等的外层异常回退；编译器又可能逐 Heap 改写正式缓存，所以不能声称任意编译失败都原子恢复。保存阶段也没有磁盘回读、版本确认或统一重试/放弃协议。因此正式采用必须把 Save 失败视作硬门禁：保留可见 Dirty、明确提示未持久化、禁止误导性成功通知，并提供重试或回到上一磁盘版本的入口；还要注入只读文件、保存异常及“API 返回但重载仍为旧内容”三类失败。

StableGuid 表示“这株实例是谁”，Heap 只表示它当前存放在哪里。Replace 保留身份只换 Prototype，Reproject 和 Select/Edit 保留身份并可跨 Heap 迁移；迁移时源、目标 Heap 同时进入受影响集，而 RuntimeIndex、排序位置、GPU 槽位、Bounds、光照和哈希都允许重建。外链只补充具体光照重绑策略，不影响理解这条身份原则。

后台或延迟 Compile 被明确写成未来协议，不是现状：只有真实大笔划测量证明同步链造成阻塞后才应引入；任务需冻结全部版本键，只生成不可变候选，完成时重新比对版本，在主线程原子交换，并拒绝 Undo、Redo、新 Commit、Prototype/Cell 变化或 Domain Reload 后的旧结果。

成本边界包括表面求交、候选生成和去重、作者查找、编译、保存及 BRG 重建。文章建议限制单笔候选数、建立 StableGuid/空间索引、分段计时并保证长操作可取消，但不虚构性能数字。正式采用的四项硬门禁是：Paint/Erase 编译失败原子恢复、Save 失败闭环、BRG Undo/Redo 三层一致性，以及 Painter 用户层 Additive Scene 选择/切换验收；异步化后还需增加旧任务丢弃和候选原子交换验证。
