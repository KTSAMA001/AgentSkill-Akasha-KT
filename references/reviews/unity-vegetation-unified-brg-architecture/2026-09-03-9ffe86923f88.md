### 2) 完整复述

本文解决的是大规模植被中“作者数据、空间组织、GPU 存储和绘制提交被错误混成一层”的问题。其基本主张是：`SceneAsset` 是唯一的持久作者数据权威，Prototype 保存一类植被共享的 Mesh、Material、LOD 和边界规则；运行时 Cell 是独立渲染与资源所有权域；Heap 只负责 Cell 内的空间归属、激活和粗剔除，不天然对应 GPU Buffer、BRG Batch 或一次绘制。

作者数据经过编译器生成连续运行数组、Bounds、地址映射和绘制分类。当前参考实现为每个已加载 Cell 创建独立 BRG 会话，上传一份包含整 Cell 实例及辅助数据的常驻 Buffer，并注册一个 BRG Batch。Batch Metadata 告诉 Shader 各属性在 Buffer 中的基址和逐实例解释方式；它不保存 Mesh、Material 或完整实例数据。

每个相机或阴影视图触发独立 BRG 剔除回调。回调先对全部 `H` 个 Heap 做活动掩码和视锥粗筛，再由 Count Job 遍历全部 `N` 个实例、做实例剔除和 LOD 选择，并按 `RenderBucketKey` 统计可见“实例—渲染部件”引用。Prefix Sum 为各桶分配 `visibleInstances` 连续区间，Scatter 再次遍历全部实例并写入批次内索引；最后只为 `D` 个非空桶生成 DrawCommand/DrawRange。DrawCommand 选择 Batch、Mesh、Material、SubMesh、Pass 及可见数组区间，Shader 再通过 Batch Metadata 和可见索引从 Buffer 读取实例记录。

文章清楚区分了四类身份：StableID 回答实例长期“是谁”；LogicalIndex 是本次运行数组位置；SharedBufferSlot 是 GPU 记录位置；BatchLocalIndex 是 BRG 交给 Shader 的实例索引；可见表位置则只是某条命令引用的数组槽。当前实现因 CPU 数组、GPU 上传和剔除数组采用相同展开顺序，使前三种运行时编号数值相等，并以 `基址 + 索引 × 32` 寻址。这是当前 ABI 的硬约束，不是 BRG 的通用规律；未来分页或重排必须通过 Batch 基址、连续 Page 或真实索引表显式完成映射。

生命周期方面，编辑器和运行时应共享后端协议，但各所有权域仍持有隔离会话；同一实例集合只能有一个提交者。Painter 只能通过预览和正式变更通道接入，不能长期拥有 BRG 资源。当前实现卸载前只确认最后的 CPU Culling Job 完成，未证明 GPU 已退役；严格热刷新、版本化快照、租约和 GraphicsFence 均被明确列为接口要求或未来方案。

空间流送进一步区分 Desired、Loaded 和 Active。当前实现没有 Heap 级异步装卸：整 Cell 数据一起驻留，兴趣范围只改变 `ActiveHeapMask`，因此不可见 Heap 能减少后续精细工作和输出，却不能缩短 Count/Scatter 的两次全实例遍历。文章给出了单视图 `O(H + B + N + P)`、一帧多视图 `O(K(H + B + N) + ΣPᵥ)` 的 CPU 成本，以及当前 Buffer 主体容量和整块/局部上传边界。

刷新和失败恢复被写成规范性事务：在旧会话外构建候选资源，完整校验后原子切换；失败时仅销毁候选并保留旧会话；切换后禁止新读取者取得旧状态，等待已有 CPU Job，并通过 Fence 或资源世代处理 GPU 使用后再释放。正文明确说明参考实现尚未验证候选隔离、故障回滚、GPU 退役及相关异常路径。

最后，文章把结论限定在“整 Cell 可驻留且可以接受每个视图全量扫描”的场景。分页、紧凑工作集、按视图 LOD 历史和严格退役只应在目标设备实验支持后采用。冻结提交/tree 只能支撑具名静态观察，不能替代故障注入、完整模式切换、GPU 捕获或设备性能测试。
