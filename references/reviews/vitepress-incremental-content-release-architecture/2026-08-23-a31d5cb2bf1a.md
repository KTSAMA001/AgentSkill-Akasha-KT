4. 读者原始复述

事故起点是：一台约 2 GB 内存的生产服务器把每次 Markdown Push 都当成 VitePress 整站构建，因而重复解析所有文档、生成全部页面和搜索数据、执行 SSR 并打包前端程序，最终触发 OOM；如果发布脚本还提前清空线上目录，构建失败会进一步造成网站不可访问。目标是让内容自动上线，但单篇变化不再重建整个程序，同时保证失败时旧版始终可读，并保留原有 URL、静态首屏和交互体验。

文章提出的核心方案不是修改 VitePress 使其支持单页构建，而是建立独立内容发布平台：程序在本地或 CI 构建为不可变版本；服务器上的受限工作器只处理内容变化。两者并非完全解耦，而是通过带版本的内容契约和 `programId` 绑定兼容组合。每篇内容同时保存标准化 Markdown、中立的语义 HTML、元数据、目录、资源和搜索信息；页面、目录、搜索和统计则是可重建的派生结果。

浏览器访问无扩展名文章 URL 时，Nginx 从 `content/current` 指向的不可变内容版本中直接返回预生成 HTML；HTML 已含正文，并引用确定程序版本的 CSS 和 JavaScript，浏览器脚本只负责搜索、主题、复制和 Mermaid 等增强。服务端不会在请求时解析 Markdown。程序资源使用不可变版本 URL，避免内容切换后误载另一版程序。

增量范围由上一版 `manifest.json` 与新输入比较决定。账本记录源提交、契约版本、程序版本、内容规则、投影规则、表现规则以及每篇文档的输入摘要和产物路径。文档新增、修改、删除、资源变化、元数据变化、搜索规则变化、主题变化和内容规则变化分别触发不同失效范围；只有内容字段或全局语义变化才有意全量重编译。所谓增量是昂贵工作随变化文档数量增长，并不要求搜索索引等每个输出文件都只能局部改写。

发布先在隔离目录生成并验证完整候选，然后在同一文件系统中原子替换 `content/current`，失败则保持或切回已验证旧版。这个“原子”明确只保证单次文件查找落入完整旧目录或完整新目录。若一个页面后续发出的搜索、图片、JSON 等请求也必须属于同一快照，这些资源还必须使用内容版本 URL或摘要地址，并保留旧版本直到活跃请求和缓存安全窗口结束。两个独立的 current 指针不能自动提供跨请求事务；更强做法是先部署不可变程序和内容资源，让账本绑定程序版本，最后只切换读者使用的内容入口。

Webhook 只是触发信号，服务器应自行确认远端主分支最新提交，并通过签名校验、持久目标、通知合并和串行 Git 状态切换收敛到最新状态。资源控制同时使用 Node.js 堆限制和覆盖整个进程组的 cgroup 限制，边界无法设置或回读时拒绝运行。

迁移顺序从盘点全局依赖、定义契约和生成全量基线开始，经过表现适配器、账本、候选切换、影子 Webhook、目标机资源测量和浏览器回归，最后才关闭服务器整站构建。若新链路不能稳定追上主分支，则恢复旧静态目录和旧 Webhook。

这套方案适合内容多、更新频繁、程序变化少、服务器资源有限且重视静态 HTML/SEO 的站点；不适合小站、已有可靠 CI/CDN 全量发布的站点，或无法承担自定义编译器、兼容契约、搜索投影和回滚维护成本的团队。案例数字只说明特定规模和技术栈下的观察结果，不是普遍性能承诺。最终行动是逐项通过采用检查；任一项不能确认，就保留旧链路或继续影子运行。
