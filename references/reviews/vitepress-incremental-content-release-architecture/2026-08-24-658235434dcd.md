读者复述：
文章解决的真实问题不是“怎样让 VitePress 原生只构建一页”，而是：小内存生产服务器把每次 Markdown 更新都当成整站程序构建，重复解析全部文档、生成路由和 HTML、打包前端并重建搜索，可能触发 OOM；若发布脚本还先清空线上目录，失败会进一步导致网站中断。

核心架构是把程序发布和内容发布拆开。程序包在本地或 CI 构建，包含页面表现、CSS、JavaScript 和内容工作器；服务器上的受限内容工作器只处理 Markdown、图片及搜索、目录、统计等内容派生物。二者并非完全独立，而是通过带版本的内容契约和 `programId` 绑定兼容组合。每篇文档会形成同时包含标准化 Markdown、主题无关语义 HTML、元数据、目录、资源和搜索字段的中立内容对象；表现适配器再据此生成保留原 URL、首屏静态正文和现有交互的页面。Nginx 直接从 `content/current` 指向的不可变内容快照返回静态 HTML，页面引用不可变程序版本资源，不在请求时解析 Markdown。

一次内容更新的流动是：GitHub Webhook 仅负责通知；服务器验签后，在同步锁内重新确认远端主分支最新提交，而不信任通知到达顺序。工作器把新输入与上一版 `manifest.json` 比较，根据文档摘要及内容、投影、表现等规则指纹判断失效范围，只编译必要内容并生成隔离候选目录；候选经过账本、页面、内容 JSON、资源、搜索和程序兼容性检查后，才原子切换 `content/current`。重复通知若目标版本已生效则直接结束。

增量失效边界也被明确区分：单篇新增或修改只重编该篇；删除会从候选页面、目录和搜索中移除；资源变化只重新散列和复制相关资源；搜索或统计规则变化只重建轻量派生数据；模板或主题变化从已有内容对象重绘页面，不重读源 Markdown；内容字段、Markdown 编译规则或全局语义变化则有意触发全量重编。文章强调“增量”约束的是昂贵解析工作与变化量的关系，并不保证搜索总索引等每个输出文件都只发生局部字节修改。

发布与回滚以不可变程序版本、不可变内容版本和账本绑定的兼容组合为边界。先放好所有版本化资源，再让候选 HTML 引用确定的程序版本，最后只切换读者入口；失败时把入口切回已验证的旧内容版本，旧账本仍绑定保留的旧程序版本。文章还正确限定了原子性的含义：指针切换只能保证一次文件查找不会落到半成品，不能自动保证同一浏览器会话的后续资源请求仍属于同一内容快照；若需要该保证，搜索、图片和内容 JSON 也必须采用版本化或内容摘要 URL，并保留旧版本至安全窗口结束。
