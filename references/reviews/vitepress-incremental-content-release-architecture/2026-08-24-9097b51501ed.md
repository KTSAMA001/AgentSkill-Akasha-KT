读者复述：

文章解决的真实问题不是“如何优化 Markdown 转 HTML”，而是避免生产服务器因一次内容提交重新执行 VitePress 的整站路由生成、SSR、前端打包和全文索引，从而在约 2 GB 内存环境中 OOM，甚至因预先清空线上目录而扩大故障。

核心架构把发布拆为两条受版本契约约束的链路：

- 程序包在本地或 CI 构建，服务器只校验并保存不可变程序版本。
- 受限内容工作器在服务器读取变化的 Markdown，生成主题无关的内容对象、语义 HTML、页面、搜索和目录等派生结果。
- 表现适配器把中立内容套入现有主题；VitePress 不再参与生产内容编译。
- Nginx 直接提供 `content/current` 下的静态 HTML，页面通过不可变版本 URL 引用与账本中 `programId` 匹配的 CSS 和 JavaScript。

一次内容更新从 GitHub Webhook 开始。服务器先验 HMAC，随后自行确认远端主分支最新提交；通知只充当门铃，重复、延迟和乱序通知不会成为发布事实。工作器持久化并合并目标，在 Git 状态锁内取得目标版本，将新输入与上一版 manifest 比较：只重新读取和编译变化文档或资源，并从内容契约更新搜索、统计和目录等投影。结果先写入隔离候选目录，经账本、页面、资源、搜索及程序兼容性验证后，再在同一文件系统内原子切换 `content/current`。

增量失效边界是：

- 单篇新增、修改、删除只失效相应页面及受影响的派生数据；
- 单个资源或元数据变化只处理关联对象；
- 搜索索引即使整体重写，也不等于重新解析全部 Markdown；
- 页面模板或主题变化可从已有内容契约重绘页面；
- 内容字段、Markdown 编译规则或全局语义变化会有意触发全量重编译；
- 同一提交重复通知应成为无操作。

发布原子性首先只保证一次文件查找落在完整旧目录或完整新目录，并不天然保证一个浏览器会话中的后续搜索、图片和 JSON 请求仍属于同一内容快照。需要会话级一致性时，这些资源也必须采用内容版本或摘要 URL，并保留旧内容与旧程序资源。两个 `current` 指针不能组成跨请求事务，因此更强方案是先部署不可变程序和内容资源，让内容账本绑定 `programId`，最终只切换读者入口；回滚则切回绑定旧程序版本的旧内容目录。

正文报告的实测证据包括：约 200 篇文档的冷迁移约 9 秒、工作器进程 RSS 峰值约 212 MiB；重复提交约 1.7 秒确认无变化；一次真实 GitHub 提交变化 3 篇、复用其余 206 篇，约 1.25 秒、RSS 峰值约 180 MiB，并覆盖平台投递至线上静态页面的链路。一次程序升级验证了预构建包校验和生产切换，但因内容实现指纹同时变化而全量重生成 209 篇，不能作为普通单篇增量证据。文章还报告候选失败、指针保持与回滚的自动化测试，以及真实域名下的直链、搜索、主题、复制和移动端回归。它明确没有在生产制造 OOM，RSS 也不等于整机或整个进程组内存；这些数字只是案例容量参考。
