读者复述：

文章解决的真实问题不是“怎样让 VitePress 原生只构建一页”，而是避免一次 Markdown 更新在小内存生产服务器上触发全站 Markdown 解析、SSR、路由生成、前端打包和搜索重建，进而 OOM，甚至因提前清空线上目录而使网站不可用。

核心架构把发布拆成两条链路：

- 程序发布在本地或 CI 构建主题、CSS、JavaScript 和内容工作器，服务器只校验并激活不可变程序包。
- 内容发布由服务器上的受限工作器处理 Markdown、资源、页面、目录、搜索和统计。文档先编译成带版本的中立内容对象，保存 Markdown、语义 HTML、元数据、目录、资源和搜索字段，再由表现适配器生成当前界面的静态页面。
- 程序与内容并非彼此独立，而是通过内容契约、`contractVersion`、`programId` 和各类规则指纹绑定兼容关系。
- Nginx 直接从 `content/current` 指向的不可变内容版本返回静态 HTML；页面引用带程序版本号的不可变 CSS/JavaScript，因此服务器不会在访问时解析 Markdown。

一次内容更新的完整流动是：GitHub Webhook 经 HMAC 验签和仓库、分支、路径白名单后，只作为唤醒信号进入持久队列；工作器重新确认远端主分支最新提交，并在同步锁内处理 Git 状态。它将新输入与上一版 manifest 比较，据摘要和规则指纹决定失效范围；变化文档被读取、编译并生成页面，未变化产物复用，目录、搜索等派生结果按需更新。所有结果先写入隔离候选目录，经过账本、页面、资源、搜索及程序兼容性验证后，才原子切换 `content/current`；旧版继续保留以供回滚。

增量失效边界不是“每个输出文件只能改几个字节”，而是昂贵的 Markdown 解析是否主要随变化文档数量增长：

- 单篇新增或修改只编译该篇；删除会从候选页面、目录和搜索中移除对应项。
- 资源变化只处理相应资源，索引元数据只使相关文档与派生数据失效。
- 搜索或统计规则变化可重建派生数据而不重读 Markdown。
- 页面模板或主题变化可从已有内容对象重绘页面。
- 内容契约、Markdown 编译规则或全局语义变化必须有意全量重编译。
- 重复通知在确认当前版本后直接结束。

发布原子性首先只保证单次文件请求落在完整旧目录或完整新目录，并不自动保证一个浏览器会话内的 HTML、搜索、图片和内容 JSON 全部来自同一内容快照。若需要后者，内容资源也要使用版本化或摘要命名 URL，并按活跃请求和缓存窗口保留旧版本。程序与内容的两个当前指针也不能组成跨请求原子事务，所以更强协议是先放好不可变资源，让内容账本和 HTML 固定引用兼容的 `programId`，最后只切读者入口；回滚则切回旧内容入口及其已绑定、仍保留的旧程序版本。

实测证据证明的是：

- 隔离测试覆盖单篇新增、修改、删除的失效语义，以及候选失败、指针保持、回滚和从已有内容对象重绘页面。
