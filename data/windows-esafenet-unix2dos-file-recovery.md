# Windows 亿赛通保护文件被 unix2dos 原地处理后的拒绝访问事故复盘

**标签**：#windows #tools #troubleshooting #experience
**来源**：实践总结
**收录日期**：2026-08-24
**状态**：✅ 已验证
**可信度**：⭐⭐⭐（限定版本事故复现、文件层恢复与 Unity 工程验收；无事故前摘要和厂商机制证据）
**适用版本**：Windows；Cobra DocGuard Client 5.2.0；WinLibs unix2dos 7.5.4

### 概要

受亿赛通透明保护的文本文件被 `unix2dos -f` 原地处理后，可能出现“文件名仍在，但普通读取、复制和重命名均被拒绝”。本案例通过可丢弃副本确认了直接触发因素，并从故障容器得到五个可编译的源码候选；其中三个可由已复现的换行字节变化直接逆转，另外两个依赖事故上下文筛选，只能称为高置信候选。

这是一份限定版本的事故复盘和风险边界，不是可直接照抄的通用恢复教程。没有事故前 SHA-256、可信备份或等价独立证据，就不能证明候选与事故前内容逐字节相同，也不能证明时间戳、ACL、保护状态等文件系统元数据已经恢复。

### 内容

> **先停止写入。** 不要在唯一故障副本上继续原地转换、覆盖、删除或“试几个参数”。先保全故障目录项和可获得的隔离导出，再决定是否继续。

#### 能确认与不能确认

| 能确认 | 不能确认 |
|---|---|
| 在指定版本组合和可丢弃副本上，`unix2dos -f` 是拒绝访问的直接触发因素。 | 亿赛通驱动内部为何拒绝原目录项，以及其校验、进程策略和视图切换算法。 |
| 命名导出的普通字节视图包含 `E-SafeNet ... LOCK` 容器头。 | 所有亿赛通版本、所有同名转换工具或所有受保护文件都具有相同字节行为。 |
| 三个文件可由一次与已复现故障相反的换行处理直接得到严格 UTF-8 C#。 | 另外两个依赖事故上下文筛选的候选就是事故前逐字节原文。 |
| 五个候选、恢复包和写回原路径的同视图明文 SHA-256 一致。 | 候选与事故前文件相同；事故后副本不能充当事故前基线。 |
| 恢复后的 Unity 工程重新导入、编译和目标测试均通过。 | 未被测试覆盖的全部语义和运行时行为绝对正确。 |

#### 场景与症状

事故发生在 Windows 上受 Cobra DocGuard Client 5.2.0 透明保护的 C# 文件。透明保护意味着磁盘上可以保存厂商容器，授权程序平时由驱动获得明文视图。

一次 WinLibs unix2dos 7.5.4 的 `unix2dos -f` 原地处理成功退出后，出现以下现象：

- 文件名和目录项仍存在；
- 编辑器、PowerShell、Git、构建工具及普通复制、移动、重命名都被拒绝；
- 管理员权限下现象不变；
- 普通 ACL、所有者、EFS 状态和附加数据流检查没有找到足以解释故障的异常；
- `unix2dos -i` 仍能检查故障项；
- 对可丢弃的正常受保护副本执行同一操作，可以稳定复现拒绝访问。

最后一项只证明“该命令是这个版本组合下的直接触发因素”，不等于已经知道保护驱动的内部根因。

#### 术语与视图

- **故障原项（S1）**：事故后的原目录项。普通程序无法打开，但必须冻结保全。
- **隔离导出（S2）**：从 S1 命名输出到新路径的故障数据副本。它不是事故前备份。
- **保护容器视图**：普通字节读取看到厂商容器头和容器数据。
- **透明明文视图**：保护驱动向普通读取 API 返回可读 C#。
- **恢复包**：写回前固化的候选、副本、工具版本、操作记录、摘要和验证结果。
- **同视图摘要**：只有双方都是容器视图，或双方都是透明明文视图时，SHA-256 才能直接比较。

本案例中，不同程序在不同阶段看到过容器视图和透明明文视图。因而“S2 有容器头，S3 普通读取是 C#”不能解释成转换工具删除了容器头；更谨慎的表述是：反向处理后，保护驱动再次向普通 API 提供了明文视图，具体切换机制未知。

#### 实际状态链

| 状态 | 本案例中的生成方式 | 普通 API 实测视图 | 证据边界 |
|---|---|---|---|
| S0 正常受保护文件 | 事故前状态 | 通常为 C# 明文 | 没有事故前 SHA-256 |
| S1 故障原项 | 一次原地 `unix2dos -f` 后 | 拒绝访问 | 只能冻结，不能继续原地试写 |
| S2 隔离导出 | 从 S1 命名输出到经可丢弃副本验证的新路径 | 可见保护容器字节 | 代表性样本与 S1 等长；该限定不能推广到所有文件 |
| S3 直接候选 | 从 S2 工作副本执行一次与故障相反的换行处理 | 三个文件成为严格 UTF-8 C# | 对另两个含事故前原生 CRLF 的文件会多删合法 CR |
| S4 事故上下文候选 | 从保全的 S2 生成有限候选，并结合事故中的实现上下文筛选 | 两个文件得到可编译的高置信 C# 候选 | 筛选证据不独立、不公开，不能作为陌生读者可复现的恢复算法 |
| S5 写回与验收 | 先固化恢复包，再经授权写回原路径 | 普通读取恢复 | 同视图明文摘要一致；工程层另行验收 |

#### 已复现的换行歧义

隔离样本显示，故障操作把普通 LF 扩成 CRLF，也会把原生 CRLF 扩成两个 CR 加 LF：

```text
事故前 LF：        0A
故障后：           0D 0A
直接逆转：         0A

事故前 CRLF：      0D 0A
故障后：           0D 0D 0A
正确逆转：         0D 0A
```

因此“删除所有 CR”不是安全规则：它能恢复普通 LF，却会破坏事故前合法 CRLF。三个文件没有遇到这项歧义；另两个文件需要决定哪些 CR 属于事故前内容。

本事故中，候选筛选使用了正在进行的实现任务里已知的类型、成员、字符串和功能行为，并由后续 Unity 编译及目标测试支持。由于这些约束不是事故前哈希、独立备份或可公开复核的完整证据，本文不发布 S4 的枚举算法，也不把“筛选后只剩一个候选”升级为“唯一正确恢复”。在另一次事故中，如果没有事故前差异、编辑器历史、可信类型清单、备份或厂商工具，应停止在候选阶段，而不是用一般源码结构自行认定原文。

#### 安全响应决策

| 阶段 | 只有满足时才继续 | 立即停止的情况 |
|---|---|---|
| 现场保全 | 原故障项保持不变；已记录文件名、大小、时间、工具版本和操作次数 | 唯一副本已被多次原地改写，操作次数不可确定 |
| 隔离复现 | 可丢弃的正常受保护副本能稳定复现同一症状 | 版本不同、字节差异不同或复现不稳定 |
| 暂存验证 | 使用全新、排他占用的暂存目录；可丢弃副本证明命名输出、工具读取和普通 API 读取行为稳定 | 输出路径已存在、目录行为未验证或不同程序视图不稳定 |
| 候选生成 | 每个候选来自保全的 S2 工作副本并写到新路径；变化能够由已复现规则解释 | 出现换行以外的变化、NUL、未知控制字节或候选仍被拒绝 |
| 候选判定 | 有事故前摘要、可信备份、版本差异、编辑器历史或等价独立证据 | 只剩一般结构检查或内部上下文，仍想宣称逐字节恢复 |
| 写回 | 已固化恢复包；用户明确接受覆盖原故障目录项会改变现场证据 | 无恢复包、摘要冲突或无法回退 |
| 工程验收 | 重新导入、编译、目标测试和数据不变性检查全部通过 | 任何编译、控制台、测试或资产完整性门禁失败 |

任何基于“目标当前不存在”的路径检查都只是非原子的执行前检查：检查完成到外部工具真正创建文件之间仍有时间窗口。恢复现场应使用仅本次任务占用的全新目录，在每次调用前再次核对，并把命令、退出码和生成文件纳入恢复包；不能把 `Test-Path` 一类检查称为绝对防覆盖保证。

本文故意不提供可复制执行的转换或写回脚本。文件恢复会改变证据，且 S2/S3 的行为依赖保护客户端、工具版本、进程视图和暂存位置；陌生执行者应先使用备份、版本库、编辑器历史或厂商恢复工具。只有在这些途径不可用、现场已保全、版本和字节行为均已独立复现时，才由具备取证能力的执行者设计本机最小实验。

#### 为什么本案例能够恢复

直接证据支持以下有限解释：

1. 原地 `unix2dos -f` 改写了受保护数据中的换行字节；
2. 该改写与原目录项随后被保护驱动拒绝访问在隔离副本上可重复关联；
3. 从故障数据建立新目录项后，反向处理能够撤销已观察到的新增 CR；
4. 容器恢复到驱动可接受的状态后，普通 API 再次获得明文；
5. 候选、恢复包和写回路径的同视图摘要一致，说明固化和写回没有再次改变候选。

“原地临时文件替换破坏校验或目录项关联”仍是机制推断，不是厂商已证实的根因。

#### 工程层验收

文件层恢复完成后，在 Unity 2022.3.62f3 工程中独立执行了工程验收：

- 恢复的五个文件均为严格 UTF-8，NUL 为 0；
- Unity 重新生成编辑器程序集，编译产物时间晚于恢复源码；
- 完整 EditMode 测试 223/223 通过；
- 两个直接覆盖恢复文件行为的测试类共 23/23 通过；
- 控制台 Error/Exception 为 0；
- 测试前后场景数据资产修订号保持 466→466；
- 预览态与编辑态 SceneView 回调均被实际驱动，计数分别为 198 和 196；
- 活动场景未被测试改脏。

这些证据说明恢复候选被当前工具链和目标行为接受，并且测试没有意外修改场景数据；它们仍不能替代事故前摘要，也不能证明未覆盖行为与事故前完全相同。

#### 常见误判

- **文件存在就只是权限问题**：透明保护驱动可以保留目录项却拒绝内容访问。
- **管理员权限能解决**：本案例管理员同样失败。
- **退出码 0 就代表转换安全**：触发故障的命令本身就是成功退出。
- **命名输出等于第二次改写**：代表性样本只证明该次输出没有明显再次扩长，不能机械推导所有文件。
- **统一删除所有 CR**：会损坏事故前原生 CRLF。
- **候选与写回哈希一致就等于无损**：这只证明写回一致，不证明候选等于事故前内容。
- **编译和测试通过就等于逐字节恢复**：它只证明被测工具链与行为接受候选。
- **恢复后立即删除隔离数据**：工程验收完成且恢复包复核前，应保留 S1、S2、候选和摘要。

#### 可复用结论

可复用的不是某条转换命令，而是证据顺序：

1. 冻结现场并区分故障原项、隔离导出、候选、恢复包和写回路径；
2. 在可丢弃副本上确认直接触发因素与真实字节差异；
3. 始终区分保护容器视图和透明明文视图，只比较同视图摘要；
4. 只逆转已独立复现的变化，遇到原生 CRLF 等歧义就要求事故前或等价独立证据；
5. 写回前固化恢复包，写回后再做工程层验收；
6. 没有事故前可信摘要时，只能报告“高置信内容恢复”，不能报告“已证明无损”。
