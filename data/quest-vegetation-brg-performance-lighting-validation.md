# Quest 级移动 VR 植被 BRG 性能隔离测试与光照数据边界

**收录日期**：2026-08-19
**来源日期**：2026-08-19
**状态**：✅ 已验证
**可信度**：⭐⭐⭐⭐（实机多轮 A/B/A 采样、编辑器可视化与实现代码交叉核对；数值仅代表记录中的测试条件）
**适用版本**：Unity 2022.3 LTS、URP 14、BatchRendererGroup、Bakery L2、Quest 级移动 VR

### 概要

移动 VR 植被性能不能只用实例总数或 Draw Call 判断。一次可复核的 BRG 与普通 GameObject GPU Instancing 对比，必须固定相机、可见实例、几何、LOD、光照、质量、Eye Buffer 和刷新率，并用 BRG→GO→BRG 的 A/B/A 顺序排除热状态与采样污染。实测说明：BRG 能显著降低对象管理和 CPU 提交成本，但不会自动减少顶点、三角形、双眼栅格化、Alpha Clip 或 Overdraw；当真实草全部占满视野时，GPU 几何与覆盖压力会掩盖 BRG 的 CPU 收益。

### 内容

#### 一、先区分两种测试目的

“BRG 对比 GO”至少有两种不同问题，必须分别命名，不能把结果混在一起。

1. **渲染后端隔离测试**
   - 两侧使用相同实例变换、Mesh、材质、LOD、光照表达和相机。
   - 唯一变量是 BRG 与普通 `MeshRenderer + GPU Instancing` 的提交和对象管理方式。
   - 用于判断 Draw 提交、Renderer 生命周期和剔除组织本身的成本。

2. **实际系统基线测试**
   - BRG 使用植被系统面向静态场景优化后的数据路径。
   - GO 表示没有植被系统时的普通 Unity 做法：由场景数据临时生成 GameObject、MeshRenderer 和 LODGroup，光照走普通 Renderer 的动态 Bakery Probe 路径。
   - 该测试衡量完整方案价值，但光照数据路径也是变量，不能声称只比较了提交后端。

任何报告都应明确自己属于哪一种；否则“BRG 比 GO 快”无法追溯快在对象管理、光照、LOD、剔除还是 Shader。

#### 二、A/B/A 是最低可信切换顺序

同一应用会话内按以下顺序采样：

```text
A：BRG 稳定采样
→ B：切换普通 GO，等待一次性展开和材质准备结束，再稳定采样
→ A：切回 BRG，等待资源重新加载后稳定采样
```

第三段 BRG 用于发现热降频、资源未释放、切换失败、缓存变化和状态泄漏。如果前后两段 BRG 明显不一致，本轮不是一个可直接下结论的闭环。

采样期间出现 `Stale` 表示采样窗口内的模式、姿态、可见集合或其它关键条件已改变，该窗口不再代表稳定状态，应排除后重采，不能混入平均值。

#### 三、报告必须保存的条件

只写“8192 株”“双密度”“完整 Box”无法让第三方复现。每组至少记录以下数据：

| 类别 | 必填字段 |
|---|---|
| 植被规模 | 场景总实例数、相机实际可见实例数、激活 Heap 数、绘制命令数 |
| 空间尺度 | 植被占地区域长宽或面积、株间距、实例缩放、相机到区域的距离 |
| 几何 | Mesh 名称的通用描述、顶点数、索引数、三角形数、SubMesh 数、Cull 模式、Alpha Clip |
| 相机 | 位置与朝向或固定路线、FOV、Near/Far、是否 XR 双眼、视口比例 |
| 工作集 | 兴趣范围、Heap 尺寸、视锥内候选数、LOD 屏幕阈值与 LOD Bias |
| 渲染质量 | Quality Level、URP Render Scale、Eye Buffer 尺寸或比例、MSAA、目标刷新率 |
| 光照 | Bakery 模式与阶数、静态或动态 SH、实时灯和实时阴影是否为 0、阴影投射开关 |
| 性能 | FPS、CPU Frame Time、GPU Frame Time、主线程/渲染线程、CPU/GPU 利用率、进程内存、温度或频率状态 |
| 可复核证据 | 应用内模式标记、性能采样截图、Overdraw/Frame Debugger 截图、构建版本或产物哈希 |

“同时可见”必须是运行时剔除结果或可审计快照，不应只靠肉眼从俯视图估计。相机 Far 很大并不等于都会绘制：兴趣范围先决定候选 Heap，视锥决定相机可见候选，LOD 再决定最终保留实例。

#### 四、已完成闭环样本与正确解读

以下数值来自同一类 Quest 级设备上的稳定采样，用于展示趋势，不是其它场景的性能承诺。所有样本总数均为 8192 株，目标刷新率为 90 Hz，运行时实时灯与实时阴影为 0，光照使用 Bakery L2 烘焙结果。

| 场景条件 | BRG FPS | 普通 GO FPS | 结论边界 |
|---|---:|---:|---|
| 8192 株真实草，总数不变，视锥和兴趣范围共同限制到约 520 株可见 | 约 90.6 | 约 90.7 | 两侧都达到刷新率上限，不能据此判断谁的 GPU 成本更低 |
| 8192 株真实草在单眼主要视野内近似全部可见；单株约 640 顶点、704 三角形 | 约 19.9 | 约 19.9 | 明显受 GPU 几何、双眼栅格化和覆盖压力限制，BRG 的 CPU 优势无法提高最终帧率 |
| 8192 个较大 Bounds Box 近似全部可见；单株 24 顶点、12 三角形，但屏幕重叠仍高 | 约 83.3 | 约 71.8 | 几何/覆盖整体工作量下降后，BRG 的 CPU 与提交优势开始显现 |
| 8192 个缩小的 Bounds Box 近似全部可见，调整为低重叠布局 | 约 90.5 | 约 81.5 | Overdraw 下降后 BRG 达到刷新率上限，GO 仍受对象与提交成本影响 |

这组 Box 替换不是严格的“只改面数”实验。真实草换成 Box 会同时改变：顶点与三角形、轮廓、UV、法线/切线、Alpha Clip 覆盖、内部交叠和 Overdraw。因此它只能证明“真实草的几何与覆盖整体工作量是主要压力来源之一”，不能单独断言顶点着色器或片元着色器谁占多少。

要进一步拆分，应使用四象限实验：

| 几何 | 片元路径 | 回答的问题 |
|---|---|---|
| 真实草 | 当前植被 Shader | 实际基线 |
| 真实草 | 廉价不透明、无复杂采样 Shader | 保留几何，观察片元路径的影响 |
| Box | 当前植被 Shader | 降低几何并保留主要 Shader 路径 |
| Box | 廉价 Shader | 设备和提交路径的低工作量底线 |

#### 五、Overdraw 的判断边界

- URP Rendering Debugger 的 `Opaque Overdraw` 显示的是不透明队列/Alpha Clip 路径中的重复片元处理；它高并不表示材质使用透明混合。
- 交叉草叶、双面 `Cull Off`、密集 Alpha Clip 网格仍会产生大量不透明阶段的重复覆盖。
- BRG 把很多实例合进一个 Draw Command 后，CPU 无法像逐 Renderer 那样按每株做精细的前到后排序；但对密集草而言，逐株排序本身也可能得不偿失。
- BRG 减少 Draw Call 不等于减少片元。每株 Mesh、双眼视图、屏幕覆盖和同一像素的重复层数不变时，GPU 仍需完成相应栅格化和片元工作。
- 对移动端 TBDR GPU，应同时观察顶点处理、片元着色、Early-Z/Alpha Clip 行为、Tile 内工作量和带宽，不能只凭 Overdraw 颜色图给出单一根因。

降低 Overdraw 的优先顺序通常是：减少同屏可见株数和交叠、缩小或重做草片轮廓、降低单株内部交叉层数、使用更合适的远景 LOD/剔除、再评估 Shader 精简。只改 BRG 提交方式不会自动解决这些问题。

#### 六、LOD、视锥和兴趣范围回答不同问题

- **兴趣范围/Active Heap**：决定哪些空间块值得进入精细剔除工作集，主要减少 CPU 候选扫描和后续命令构建。某些实现会让完整实例 Buffer 继续驻留 GPU，因此 Heap 失活不必然等于释放 GPU 内存。
- **视锥剔除**：针对每个 Camera 或 Shadow View，判断候选实例是否落在可见锥体内。
- **LOD**：根据投影后的屏幕相对尺寸选择简化 Mesh 或 Cull。相机 Far 设置很远时，LOD 仍可限制最终实例数；但所有落入兴趣范围的候选仍可能参与前置计算。
- **Far Clip**：只给视锥远端一个硬边界，不能替代兴趣范围或 LOD。

因此“Far 很远，完全依赖 LOD”和“Far 较近，依赖视锥”并非等价：前者扩大候选和深度范围，可能增加 CPU 剔除与深度精度压力；兴趣范围过大还会使更多 Heap 保持激活。正确配置通常是兴趣范围控制世界工作集、视锥处理当前视图、LOD 控制可接受的屏幕尺寸。

#### 七、GO 与 BRG 的 Bakery SH 不是同一条光照路径

在经过优化的静态植被路径中：

```text
Bakery L2 Probe
→ 编辑器按每株采样位置和约定方向求值
→ 得到最终静态 RGB
→ 写入场景植被资产的 Heap
→ BRG Shader 运行时直接读取 RGB
```

普通 GO 基线则应保持 Unity Renderer 的常规行为：

```text
Light Probe / Blend Probes
→ Renderer 取得 Probe 系数
→ Shader 通过 BakeryDecodeLightmap.hlsl 的 BakerySH_float
→ 按顶点世界法线动态求值
```

两侧视觉有差异是预期结果：BRG 保存的是烘焙时已经求值的静态颜色，GO 运行时按各顶点法线评估 Bakery SH；二者不是同一信号。实际系统基线测试应保留这个差异，因为它正是系统优化的一部分；渲染后端隔离测试则必须让两侧使用相同光照表达。

禁止用 Unity `SampleSH` 作为 Bakery 路径的静默回退。需要动态 Bakery SH 时，应明确包含并调用项目适配的 `BakeryDecodeLightmap.hlsl`；变体缺失应显式失败或在构建门禁中发现，而不是默认改变光照模型。

#### 八、Prototype 与场景光照数据的所有权

植被 Prototype 只应保存可复用的采样策略：

- 使用哪种光照来源。
- 单高度或双高度。
- 归一化采样高度或锚点定义。
- 是否需要动态求值。

具体场景中的 Probe 系数、最终 RGB、Lightmap 采样结果和实例映射必须属于对应场景植被资产的 Heap。Prototype 不能保存某个场景的实例、Heap 或 SH/RGB 数据，否则同一原型被多个场景复用时会发生交叉污染。

单纯修改 LOD 屏幕阈值不应使 SH 过期。只有修改了会改变采样位置或语义的数据，例如可视 Bounds、采样锚点、单/双高度模式或光照来源，旧光照缓存才需要重新采样。刷新工具应报告“旧值→新值”的具体变化，不能只显示笼统的 Stale。

#### 九、光照选项应拆成三个维度

把“单高度 Probe、双高度 Probe、精确 Lightmap、动态光”塞在一个枚举里，会把光照来源、采样数量和运行时表达混在一起。更清晰的策略是：

1. **光照来源**：Bakery Probe L2、地表 Lightmap、无烘焙光照。
2. **空间采样**：单高度、双高度。
3. **运行时表达**：静态 RGB、动态 Bakery SH、运行时 Lightmap。

推荐组合：

- 矮草：Bakery L2 → 单高度静态 RGB。
- 高草/灌木：Bakery L2 → 根部与顶部静态 RGB，按顶点高度插值。
- 静态草且地面已有高质量 Lightmap：编辑器读取地表 Lightmap → 写成每株静态 RGB。
- 会移动或被提升为普通对象的植被：动态 Bakery SH。

“编辑器读取地表 Lightmap 后写静态 RGB”与“运行时直接采 Lightmap”不是同一方案。后者需要每株 Lightmap Index、UV 或世界到图集映射、纹理绑定与批次兼容管理，增加实例数据、纹理带宽和驻留复杂度；对于不移动的 Quest 植被，前者通常更合适。

双高度对短草通常收益很小，却会增加顶部颜色记录、Buffer 读取和插值。制作界面应按模式显示字段：单高度只显示 Root，双高度显示 Root/Top，动态或不使用高度锚点的模式不应继续展示无效项。

#### 十、构建与测试常见误判

- 编辑器与 Android/Quest 使用不同 Quality Level、URP Asset、实时阴影或 Eye Buffer 时，所有性能数据需要重测。
- 设备刷新率上限不同会直接改变 CPU/GPU 利用率外观；72 Hz 和 90 Hz 数据不能直接横向比较。
- 降低分辨率后性能没有变化，只能说明当时不明显受像素分辨率限制，不能单凭一次观察排除片元或带宽问题。
- 低 FPS 时 CPU 利用率变低，可能只是 GPU 阻塞使 CPU 提交频率下降，不表示高面数模型让 CPU 更省。
- 面板显示“场景总数”不能替代“实际绘制数”；BRG 未加载或 Draw Command 为 0 时，仍显示总实例数会制造虚假的高性能样本。
- 早期包含实时灯、实时阴影、质量档不一致或缺少关键相机数据的样本只能作为排查历史，不能并入正式范围估计。
