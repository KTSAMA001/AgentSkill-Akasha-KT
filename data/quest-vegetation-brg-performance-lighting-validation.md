### 概要

本记录只采用四组完成“初始 BRG → 普通 GO → 回切 BRG”三段采样的 Quest 3S 数据。最明确的结论是：BRG 主要降低大量普通 `GameObject + Transform + MeshRenderer + LODGroup` 所经过的 CPU 路径；它不会自动减少已经进入视野的顶点、三角形、双面栅格化、Alpha Clip 和重复像素覆盖。

8192 株约 5 米高、单株 640 顶点/704 三角形的真实草在设备上 8192/8192 可见时，BRG 与普通 GO 都约 20 FPS、GPU 利用率约 99%。跨构建观察中，把网格换为单个 24 顶点/12 三角形的 Box 并进一步缩小实际屏幕覆盖时，BRG 为 83–91 FPS，普通 GO 在各自同包 A/B/A 中表现出更高的 CPU 侧总压力；由于两个 Box APK 还存在 31.111% 未解释的体积差异，这一跨构建结果只与几何和覆盖成本重要的判断一致。现有 Box 对照同时改变几何拓扑、轮廓、Alpha Clip 覆盖和 Overdraw，不能把收益精确拆分成顶点、三角形或片元各占多少。

四组测试中的 BRG 使用逐株静态最终颜色；普通 GO 使用 Unity BlendProbes 与 Bakery SH 运行时路径。这是完整系统路径对比，不是只替换 Draw API 的微基准。

#### 二、测试对象、场地和相机参考尺度

**真实草。** 单株 LOD0 为 640 顶点、704 三角形、2112 索引、1 个 SubMesh。实际几何 Root Space AABB 为 `0.3154 × 0.4634 × 0.3642` 米，实例缩放为 10.8–12.6 倍，世界尺寸约为 X `3.41–3.97` 米、Y `5.00–5.84` 米、Z `3.93–4.59` 米。材质使用 Alpha Clip 与 `Cull Off`。本记录中的“真实草”只指这一测试模型。

**高密度场地。** 共 8192 株、50 个 Heap；实例中心范围约 `158.99 × 78.99` 米，面积 `12558.22` 平方米，平均密度 `0.652` 株/平方米，等效平均中心间距约 `1.24` 米，实际最小中心距离 `1.014` 米。XR Rig 位于 `(0,100,0)` 并绕 X 轴 90°俯视，相机在 Rig 下保留约 1.6 米局部高度，头显跟踪仍启用。Near/Far 为 `0.03/300` 米，单眼 FOV（水平 × 垂直）约 `90° × 98°`，Eye Buffer `1536 × 1760`、Viewport `100%`，刷新率 90 Hz，质量档为 Performant。Heap 加载/卸载范围为 `180/200` 米，LOD 为单档、Cull 0、LOD Bias 100。探针源为 Bakery L2；三盏灯均已烘焙，运行时实时灯数量为 0。

真实草组保存了 Active Heaps `50/50`、Frustum Candidates `8192`、Visible After LOD `8192/8192`、植被 BRG Draw Command `1`、GO Visible `8192/8192`。这里的 Draw Command 1 只指植被 BRG 命令，不等于整个 GameView 只有一个 Draw Call。

**稀疏大场地。** 总量 8192 株、1024 个 Heap；设计场地 `504 × 504` 米，SceneAsset 实例中心实际范围约 `504.59 × 504.60` 米；网格间距 X `3.97` 米、Z `8.00` 米。XR Rig 可移动，Near/Far 为 `0.03/1000` 米，FOV（水平 × 垂直）约 `104.09° × 80°`，刷新率 90 Hz，Heap 加载/卸载范围 `150/175` 米，LOD Bias/Cull 为 `0.2/0.005`。设备三段没有保存姿态、Eye Buffer、质量档、光照配置和实际可见数。

编辑器默认姿态曾记录 Active Heaps `320/1024` → Frustum Candidates `2595` → Visible After LOD `520/8192`；该 520 不代表三段设备采样期间的实际可见数。

#### 三、两种 Box 代理准确代表什么

大尺寸 Box 与 15% 尺寸 Box 都是 24 顶点、12 三角形、36 索引。大尺寸 Box 的实际几何 Root Space AABB 与真实草相同；15% 尺寸 Box 的实际几何 AABB 为 `0.0473 × 0.0695 × 0.0546` 米，缩放后世界尺寸约 X `0.51–0.60` 米、Y `0.75–0.88` 米、Z `0.59–0.69` 米。15% Box 的最大方向无关包围圆直径 `0.911` 米，小于最小中心距 `1.014` 米，因此实际几何不相交；BRG 保守剔除 Bounds 仍保持真实草大小。

用户在头显全景构图中观察到两组 Box 的 8192 个实例全部进入画面，设备截图保存了该构图；三段未保存统一机器可见计数。头显观察与截图支持“全部入画”的观察结论，但不等价于程序化 `8192/8192` 可见计数。

真实草换成大尺寸 Box 时，同时改变了网格拓扑、草叶轮廓、Alpha Clip 覆盖和内部 Overdraw。大尺寸 Box 再缩到 15% 时，两个构建报告记录的实例总数、材质、LOD 参考参数、SH 字节摘要和相机参数一致，但两个 APK 的体积分别为 `270621866` 与 `186428728` 字节，相差 `84193138` 字节，即相对大尺寸 Box APK 减少 `31.111%`。这一跨构建漂移没有被解释，故：

- 各自包内 BRG→GO→BRG 的比较可直接使用；
- 跨真实草、大 Box、15% Box 的比较只作为相关性证据；
- 不能把跨包差异称为严格单变量证明。

#### 四、如何解释 CPU、GPU、Overdraw 与内存

**GPU。** 高密度真实草三段 GPU 利用率约 99%、FPS 约 20，说明该条件下 GPU 工作量是主要瓶颈。8192 株 × 704 三角形约为 576.7 万个实例三角形；双眼、Cull Off、Alpha Clip 和遮挡层叠还会继续增加工作量。现有跨构建对照只与“真实草几何与覆盖的组合成本重要”的判断一致，不能拆分顶点、三角形、Alpha Clip 与片元各自占比。

**CPU。** 大尺寸 Box 与 15% 尺寸 Box 中，普通 GO 的 CPU 利用率明显高于两段 BRG，且回切后恢复，支持普通 GO 完整路径的 CPU 侧总压力更高。没有主线程、渲染线程、Renderer、LOD、动态探针绑定和 Draw 提交分项，不能把差值唯一归因于其中一个环节。

**Overdraw。** Alpha Clip 植被通常在不透明队列绘制，所以会出现在 Opaque Overdraw 视图中；Transparent Overdraw 没有颜色不代表没有重复片元成本。Cull Off、草叶交叉、密集实例、较大屏幕尺寸和双眼都会增加工作量。BRG 减少 Draw Command，不会自动减少已经进入视野的几何或片元成本。

**Stale。** 这是 VrApi 报告字段，本记录按“合成器在应用未及时提交新帧时复用旧帧”的常见含义解释；它不是植被光照缓存过期。高密度真实草约 72 Stale/s 与约 20 FPS 一起表明应用明显跟不上 90 Hz。

**内存。** Total PSS 是 Android `dumpsys meminfo` 的整个应用进程分摊内存，原始单位 KB。普通 GO 段相对初始 BRG 分别增加约 `75.473 / 45.568 / 66.998 / 40.193 MiB`（稀疏、真实草、大 Box、15% Box）；这些值由 KB 差值除以 1024 得到。PSS 包含 Unity、XR、代码、纹理、图形资源与分配器保留，不能全部归因于 GameObject，也不能仅凭回切残留判断泄漏。

#### 五、BRG、普通 GO 与 SH 的实际差异

四组性能 APK 中：

- **BRG** 使用 `StaticLightColor`。刷新阶段在每株 `VisualRootSpaceBounds.center` 取得完整 L2 探针，以实例局部向上方向求出最终 RGB，并写入 SceneAsset/Heap；运行时直接读取最终颜色。
- **普通 GO** 从同一 SceneAsset 的实例变换展开 GameObject、Transform、MeshRenderer 与 LODGroup，材质启用 Unity GPU Instancing；Unity BlendProbes 按位置取得探针。Bakery 的非 Lightmap Shader 路径消费 `unity_SHAr/Ag/Ab` 的 L0/L1 表示，并按顶点法线执行 Geomerics 重建。

稀疏组的一手设备报告也直接记录了上述 BRG/GO 光照代码路径；但该组没有保存场景灯、探针布置、Eye Buffer、质量档等配置，所以不能把其画面或性能差异进一步归因到具体光照配置。

因此，“探针烘焙模式为 Bakery L2”不等于两条运行时路径都在 GPU 上完整评估 L2。BRG 的完整 L2 已在刷新阶段求成最终 RGB；普通 GO 运行时使用 Ar/Ag/Ab 表示。两侧颜色和运行成本都不是严格等价。

逐株场景光照属于 SceneAsset/Heap，不属于可跨场景复用的 Prototype。Prototype 保存 Mesh、材质、LOD、Bounds、碰撞与光照模式声明；SceneAsset 保存实例变换、空间分组和该场景烘焙得到的逐株光照记录。

#### 六、当前 v4 光照能力与测试 APK 的版本边界

当前正式实现只有两种 Prototype 可选 BRG 光照模式，且两者都只在每株 `VisualRootSpaceBounds.center` 采样一次：

| 当前模式 | 刷新阶段 | Heap 每株记录 | 运行时 | 适用对象 |
|---|---|---:|---|---|
| `StaticLightColor` | 取得完整 L2，以实例局部向上方向求最终 RGB | 8 字节 | 直接读取最终颜色，不按每顶点法线重算 | 静态、数量大、优先降低逐株光照数据带宽与顶点光照计算的植被 |
| `StaticBakerySh` | 从 L2 来源提取 Bakery Ar/Ag/Ab 表示 | 20 字节 | 按顶点法线执行 Geomerics L1 评估 | 需要保留法线方向变化、但仍希望避免普通 GO 动态探针绑定的植被 |

当前数据版本 v4 已移除 Root/Top 双高度格式；Lightmap 也不是当前枚举选项。`StaticBakerySh` 存在于当前实现，但没有进入本文四组性能 APK。

本文实机数据对应 2026-08-19 的测试 APK，不等同于当前 v4 数据布局的实机验证。至少大尺寸 Box 的历史构建报告明确记录旧格式 Root 静态 RGB 为 `98304 / 8192 = 12 字节/株`，Top 为 0；当前 v4 已改为上表的 8 字节或 20 字节记录。

双高度采样与 Lightmap 只能作为后续扩展提案：

- 双高度可为高草或灌木分别记录根部与顶部光照，再按顶点高度插值，但会增加每株记录和刷新成本，且不能替代完整方向性 SH；
- Lightmap 可保留更高频静态阴影细节，但需要 Lightmap UV、纹理空间、每实例映射数据、纹理带宽与更复杂的批次组织；
- 无论扩展哪种表达方式，场景烘焙结果都应留在 SceneAsset，不能写回可复用 Prototype。

#### 七、视锥、LOD 与 Heap 兴趣范围

三个机制解决不同层级的问题：Heap 兴趣范围决定哪些空间区域进入系统更新；视锥剔除排除相机外候选；LOD/Cull 根据屏幕相对高度选择网格或停止绘制。Camera Far 设得很远不会替代兴趣范围与 LOD，缩短 Far 也不能替代相机周围的空间区域管理。

当前 Heap “卸载”主要是逻辑停用：停用 Heap 不再生成可见引用和相关碰撞代理。它不等于销毁整个 SceneAsset，也不保证立即缩小已分配的 GPU 主数据缓冲。降低常驻内存还需要独立的资产分块、缓冲重建或流式上传策略。

#### 八、适用边界

- 数值只代表 Quest 3S 与本文明确列出的模型、场地、相机、刷新率、密度和光照条件。
- 稀疏组的设备可见数、Eye Buffer、质量档和光照配置没有保存，不能建立精确“可见株数→FPS”曲线。
- Box 两组的“全部入画”是用户头显观察与设备截图证据，不是程序化机器计数。
- 大 Box 与 15% Box 存在 31.111% APK 体积漂移，跨包因果强度必须降级。
- BRG 与普通 GO 光照路径不同，结果是完整系统路径对比，不是纯 Draw API 微基准。
- 头显姿态和预热时长没有程序化锁定，窗口平均值可能包含姿态差异与切换残余瞬态。
- 没有线程与子系统分项，CPU 利用率不能定位唯一子模块。
- 本文实机数据不是当前 v4 光照记录布局的实机验证。
