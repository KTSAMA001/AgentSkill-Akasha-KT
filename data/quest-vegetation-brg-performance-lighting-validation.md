### 概要

Quest 3S 实机 A/B/A 表明：8192 株约 5 m 高、640 顶点/704 三角形的双面 Alpha Clip 真实草全部可见时，BRG 与普通 GO 都受 GPU 几何和覆盖压力限制在约 20 FPS；换成 24 顶点/12 三角形代理并减少几何交叠后，BRG 可恢复到约 90 FPS，而普通 GO 完整路径仍表现出更高的 CPU 侧开销。本记录同时明确相机、密度、可见数缺口、采样口径，以及静态 RGB 与动态 Bakery SH 并非同一光照路径。

### 内容

#### 一、结论摘要

本轮比较两条完整渲染路径：

- **BRG 路径**：场景植被数据由 `SceneAsset` 管理，通过 `BatchRendererGroup` 提交；本轮使用已经写入场景资产的逐株静态 RGB 光照。
- **普通 GO 路径**：从同一份植被实例数据展开普通 `GameObject + MeshRenderer`，材质开启 Unity GPU Instancing；运行时使用普通 Renderer 的动态 Bakery SH 光探针路径。

因此，这不是“只替换 Draw API、其他条件绝对相同”的微基准。两条路径除了对象管理和提交方式不同，光照取数路径也不同。本文只在同一测试组内部比较 BRG→GO→BRG，不把跨组差异直接归因给单一模块。

在本文条件下得到四个可复用判断：

1. **BRG 可以降低大量普通 Renderer/GameObject 完整路径的 CPU 侧开销；它不会自动降低可见几何量、屏幕覆盖或像素着色成本。**
2. **8192 株大尺寸真实草同时可见时，两条路径都约 20 FPS，GPU 接近满载。** 此时后端差异被几何、Alpha Clip、双面与屏幕覆盖成本淹没。
3. **把相同场地中的真实草换成 24 顶点、12 三角形的 Bounds Box 代理后，BRG 提升到约 83–85 FPS；再把代理缩到原尺寸的 15%、消除几何交叠后，BRG 达到约 90.5 FPS。** 结果支持“可见几何与屏幕覆盖/Overdraw 是重要压力来源”，但代理组没有保存运行时可见数，且来自不同构建，不能据此把收益精确拆分为顶点、三角形或片元各占多少。
4. **同为 8192 株真实草，当场地扩大并配置较小兴趣范围与 LOD/Cull 后，两条路径都接近 90 FPS。** 由于设备阶段可见数未保存，这只能视为该整体配置的结果，不能证明三段实际绘制了较少或相同数量的植被；“520 株”只是编辑器默认姿态的诊断值。

#### 二、测试口径

##### 2.1 A/B/A 的含义

每个测试组都在同一次应用会话中按以下顺序切换：

1. A：BRG；
2. B：普通 GO + Unity GPU Instancing；
3. A：切回 BRG。

第三段用于检查模式切换后能否回到与第一段接近的状态，避免只看一次切换造成误判。

##### 2.2 采样与统计

- “样本数”表示约 **1 Hz** 读取的一次 VrApi 运行监控点，不是逐帧 Profiler 样本。
- 表中的 FPS、CPU+GPU 时序、CPU/GPU 利用率、Stale frames/s 与 PSS 都是该窗口内监控点的**算术平均值**。
- 单段窗口约 15–20 秒：16 点约 15 秒，20 点约 19 秒；稀疏大场地 GO 段为 15 点。
- 各段预热时间没有统一保存。监控窗口是否混入切换后的对象创建、Shader 准备或资源加载残余无法完全确认，因此表中均值不能严格拆分稳定运行成本与切换后瞬态成本；CPU 结论只描述已保存窗口中的完整路径差异。
- 头显姿态没有程序化锁定；同一 A/B/A 组尽量维持相同观察区域，但不能视为逐像素一致的离线基准。

##### 2.3 指标含义

- **CPU+GPU 时序**：VrApi 记录的应用侧 CPU 与 GPU 综合帧时参考值，越低越好。
- **Stale frames/s**：VrApi 统计的合成器每秒复用旧帧次数；它不是植被光照缓存“过期”。
- **PSS**：Android 进程的 Proportional Set Size，用于观察应用进程内存量级；模式切换后的资源释放时机可能影响回切数值。

#### 六、结果解释与证据边界

##### 6.1 真实草全部可见：GPU 已经成为共同上限

8192 株 × 704 三角形约为 576.7 万个实例三角形；还要考虑双眼、Cull Off、Alpha Clip、遮挡层叠和片元着色。两条路径都约 20 FPS，GPU 利用率约 99%，说明这一条件下更换提交后端不足以解除主要瓶颈。

普通 GO 的 CPU 利用率和 CPU+GPU 时序高于 BRG，说明普通 GO 完整路径具有更高的 CPU 侧开销。由于没有采集主线程、渲染线程、LOD、动态探针绑定和 Draw 提交的分项耗时，而且两条路径的光照取数不同，不能把差值精确分摊给某一个子模块。预热时长未统一保存，因此这里描述的是已记录窗口中的完整路径差异，不是严格拆除瞬态后的稳定态微基准。

##### 6.2 换成 24 顶点 Box：真实草几何与覆盖是重要压力来源

在高密度场地中，BRG 从约 20 FPS 提升到 83–85 FPS。该变化同时减少了顶点、三角形、草叶轮廓、Alpha Clip 覆盖和内部 Overdraw，因此它支持“真实草 Mesh 的几何与覆盖整体工作量是重要压力来源”，但不是严格的顶点或片元单变量证明。代理来自独立构建，头显姿态未锁定且运行时可见数未保存，这进一步限制了因果强度。

GO 仍比 BRG 慢，且 CPU 利用率明显更高。能确认的是普通 GO 完整路径具有更高的 CPU 侧开销；没有线程级和探针绑定分项，不能进一步把它定量归因到 GameObject 管理、Renderer、LOD、动态 SH 或 Draw 提交中的某一项。

##### 6.3 Box 缩到 15% 且不交叠：结果与降低屏幕覆盖有效一致

BRG 达到约 90.5 FPS，GPU 利用率从大 Box 组的约 98% 降到约 45–47%。这个结果与“缩小屏幕覆盖并消除实例几何交叠可降低 GPU 压力”一致。

不过，大 Box 与 15% Box 来自不同构建，两组均没有保存运行时可见数。它们提供强相关证据，不能作为严格单变量证明，也不能量化 Overdraw 在总收益中的精确占比。

##### 6.4 稀疏大场地整体配置：总资产量不等于单帧工作量

稀疏大场地真实草组保持 8192 个场景实例并接近 90 FPS。该组同时改变了场地面积、Heap 数、兴趣范围、相机和 LOD/Cull，且设备阶段可见数未保存，因此只能确认这套整体配置在已记录窗口内性能良好，不能证明某个单独机制或某个固定可见株数造成了结果。

系统容量评估仍应区分：

- SceneAsset 总实例数；
- 已激活 Heap 中的候选数；
- 通过视锥和 LOD 后的可见数；
- 最终 Draw Command 引用数。

##### 6.5 A/B/A 回切与内存

四组的回切 BRG FPS 都接近初始 BRG，说明正常切换路径没有表现出持续性的渲染退化。

PSS 在 GO 段通常上升，回切后不一定立即回到起点。这与 GO 展开和 Unity/Android 延迟释放资源的行为相符，但 PSS 只是进程量级指标；没有对象级内存快照，不能把全部增长都归因于 MeshRenderer 或 GameObject。

#### 七、视锥、LOD、Heap 兴趣范围与“卸载”

这三个机制解决的问题不同：

1. **Heap 兴趣范围**先决定哪些空间区域参与本帧系统更新；
2. **视锥剔除**排除相机外的候选；
3. **LOD / Cull**根据屏幕相对高度选择网格或停止绘制。

把 Camera Far 设得很远，不会替代兴趣范围与 LOD：远处对象仍可能进入更早的候选阶段。相反，只缩短 Far 也无法处理相机附近但背后的区域管理。

当前实现中的 Heap “卸载”主要是**逻辑停用**：停用 Heap 不再生成可见引用和相关碰撞代理。它不等价于销毁整个 SceneAsset，也不保证立即缩小已经分配的 GPU 主数据缓冲。若目标是降低常驻内存，还需要独立的资产分块、缓冲重建或流式上传策略。

#### 八、为什么不透明 Overdraw 视图里仍会看到草的高覆盖

Alpha Clip 植被通常在不透明队列中绘制，因此 Rendering Debugger 的 Opaque Overdraw 会统计它；“透明视图没有覆盖”不代表草没有片元浪费。

主要原因包括：

- 草叶网格大量互相遮挡，同一像素先后经过多层不透明/裁切表面；
- `Cull Off` 使正反面都可能参与处理；
- Alpha Clip 的像素仍需运行到 `clip` 判定，透明区域并非零成本；
- 实例化把很多对象合并成较少提交，但不保证同一批实例能获得理想的逐物体前到后排序；
- 双眼渲染放大可见几何与像素成本。

因此，降低 Draw Call 不能替代降低同时可见数量、几何复杂度、草株屏幕尺寸和重叠率。移动 VR 上应先控制这些直接工作量，再评估 Depth Prepass、Alpha-To-Coverage 或更廉价片元路径；这些手段可能增加 Pass 或带来画质代价，不能仅凭理论默认更快。

#### 九、光照路径与 SH 颜色差异

##### 9.1 本轮 BRG 与 GO 的光照并不完全等价

- **BRG**：读取 SceneAsset/Heap 中已经刷新好的逐株静态 RGB；运行时不再为每个像素或每个 Renderer 动态评估完整 SH。
- **普通 GO**：使用普通 MeshRenderer 的动态 Bakery SH 光探针路径，按空间位置取得 SH 系数，再结合表面法线评估方向性光照。

所以两侧颜色可能不同：静态 RGB 更接近“在刷新时把该位置的环境光结果固化”，动态 SH 会随法线方向产生差异。性能数据也同时包含了这两条光照路径的成本差别，不能把全部差异只归因于 BRG 与 GameObject 提交方式。

##### 9.2 SH 为什么需要位置和法线

SH 光照分成两步：

1. 根据世界位置取得该点的 SH 系数；
2. 用世界法线评估该方向收到的间接光。

因此，动态 SH 不是“只有法线就能采样”。位置决定处于哪一片光照环境，法线决定同一环境下朝哪个方向接收光。

##### 9.3 数据所有权

逐株场景光照属于 SceneAsset 的 Heap 数据，不属于植被 Prototype：

- Prototype 保存可跨场景复用的 Mesh、材质、LOD、Bounds、碰撞和采样定义；
- SceneAsset/Heap 保存实例变换、空间分组以及该场景烘焙得到的逐株光照数据。

修改 LOD 阈值本身不应使 SH 过期。只有当 Mesh/Renderer 改动间接改变了用于采样的 Root Space Bounds、采样高度或光照模式时，旧光照才可能与新采样位置不一致。

---

#### 十、由实现边界推导的光照设计建议（非四组实机直接验证）

本节是根据已核对的数据所有权和运行时路径提出的设计建议，不属于上面四组 Quest 3S A/B/A 性能试验的直接验证结论。

植被原型可以决定所需的光照表达精度，但烘焙结果仍应写入所属场景的 SceneAsset：

| 模式 | 运行时含义 | 适合对象 | 主要代价 / 限制 |
|---|---|---|---|
| 单高度静态 RGB | 每株在一个高度保存颜色，运行时直接读取 | 矮草、地表覆盖物、静态密集植被 | 成本最低；缺少株内垂直渐变和法线方向性 |
| 双高度静态 RGB | 每株保存根部与顶部颜色，按顶点高度插值 | 较高草、灌木、根部与顶部光照差明显的对象 | 逐株静态 RGB 光照字段约为单高度模式的两倍；实例变换等其它字段不变；仍不是完整方向性 SH |
| 动态 Bakery SH | 保存/绑定 SH 系数，运行时按法线评估 | 法线起伏明显、方向性光照重要或会移动的对象 | 带宽与 Shader 计算更高；普通 GO 还有 Renderer/探针绑定成本 |
| Lightmap | 通过 UV 读取烘焙纹理 | 少量、固定、需要高频阴影细节的植被 | 需要 Lightmap UV、纹理空间和每实例映射；大规模实例化下内存与批次组织更复杂 |

“单高度/双高度采样点”仍有用途：它们定义**烘焙或刷新时**从场景的哪个位置取得光照。静态 RGB 只是把运行时采样提前到了离线阶段，并不意味着烘焙阶段不需要位置。对于单高度模式，顶部采样点可以在界面与 Prefab 层级中隐藏；只有双高度模式才需要同时配置 Root 与 Top。

建议把原型界面明确拆成两层：

- **光照表达方式**：静态 RGB、动态 Bakery SH、Lightmap；
- **空间采样方式**：单高度、双高度。

这样“是否保留方向性”和“在植株高度上采几个位置”不会混成一个难以理解的枚举。

#### 十一、使用这些数据时的边界

- 数值只代表 Quest 3S、本文列出的相机、分辨率、刷新率、模型尺寸、密度和光照条件；稀疏大场地组未单独保存的条件除外。
- 稀疏大场地组缺少设备三段实际可见数和部分质量配置，只能说明该整体配置的结果，不适合建立精确的“可见株数→FPS”曲线。
- 两组 Box 缺少运行时可见数且来自不同构建，只能作为几何/覆盖整体压力的强相关证据。
- BRG 与 GO 光照路径不同，当前结果是“完整系统路径对比”，不是纯 Draw API 微基准。
- 预热时长未统一保存，均值可能包含切换后残余瞬态。
- 未采集主线程、渲染线程和动态探针绑定分项，CPU 利用率只能说明普通 GO 完整路径开销更高，不能定位到唯一子模块。
