### 概要

本记录只采用四组按“初始 BRG → 普通 GO → 回切 BRG”顺序保存的 Quest 3S 三段采样。只有 15% Box 保留了三段同一 PID；高密度真实草与大 Box 具有同一应用会话说明但没有 PID，稀疏组只保留顺序窗口和操作者切换说明。这些数据与“BRG 可降低大量普通 `GameObject + Transform + MeshRenderer + LODGroup` 的 CPU 路径压力”一致；它们也表明 BRG 不会自动减少已经进入视野的顶点、三角形、双面栅格化、Alpha Clip 和重复像素覆盖。

8192 株约 5 米高、单株 640 顶点/704 三角形的真实草在设备上 8192/8192 可见时，BRG 与普通 GO 都约 20 FPS、GPU 利用率约 99%。跨构建观察中，把网格换为单个 24 顶点/12 三角形的 Box 并进一步缩小实际屏幕覆盖时，BRG 为 83–91 FPS，普通 GO 在各自同包 A/B/A 中表现出更高的 CPU 侧总压力；由于两个 Box APK 还存在 31.111% 未解释的体积差异，这一跨构建结果只与几何和覆盖成本重要的判断一致。现有 Box 对照同时改变几何拓扑、轮廓、Alpha Clip 覆盖和 Overdraw，不能把收益精确拆分成顶点、三角形或片元各占多少。

四组测试中的 BRG 使用逐株静态最终颜色；普通 GO 使用 Unity BlendProbes 与 Bakery SH 运行时路径。这是完整系统路径对比，不是只替换 Draw API 的微基准。

### 内容

#### 历史实验与当前实现的边界

本文数值来自 2026-08-19 的四组 Quest 3S 测试构建。它们仍支持两条有限解释：普通 GO 完整对象路径会增加 CPU 侧压力；BRG 不会自动消除可见几何与 Overdraw。

当前实现的实例数据、光照表达和运行时组织均已变化，但**没有用同一协议重新采集 Quest 数据**。因此本文只验证历史设备观测及其边界，不代表当前 ABI、Shader 或运行链的设备性能。

#### 一、四组 A/B/A 的直接结果

#### 二、测试对象、场地和相机参考尺度

**真实草。** 单株 LOD0 为 640 顶点、704 三角形、2112 索引、1 个 SubMesh。实际几何 Root Space AABB 为 `0.3154 × 0.4634 × 0.3642` 米，实例缩放为 10.8–12.6 倍，世界尺寸约为 X `3.41–3.97` 米、Y `5.00–5.84` 米、Z `3.93–4.59` 米。材质使用 Alpha Clip 与 `Cull Off`。本记录中的“真实草”只指这一测试模型。

**高密度场地。** 共 8192 株、50 个 Heap；实例中心范围约 `158.99 × 78.99` 米，面积 `12558.22` 平方米，平均密度 `0.652` 株/平方米，等效平均中心间距约 `1.24` 米，XZ 世界空间最小中心距离为 `1.01428664` 米。边长只展示到小数点后两位，面积使用未舍入的原始边界差计算，因此不能把两个显示值相乘作为精确面积复算。XR Rig 位于 `(0,100,0)` 并绕 X 轴 90°俯视，相机在 Rig 下保留约 1.6 米局部高度，头显跟踪仍启用。Near/Far 为 `0.03/300` 米，单眼 FOV（水平 × 垂直）约 `90° × 98°`，Eye Buffer `1536 × 1760`、Viewport `100%`，刷新率 90 Hz，质量档为 Performant。Heap 加载/卸载范围为 `180/200` 米，LOD 为单档、Cull 0、LOD Bias 100。探针源为 Bakery L2；三盏灯均已烘焙，运行时实时灯数量为 0。

真实草组保存了 Active Heaps `50/50`、Frustum Candidates `8192`、Visible After LOD `8192/8192`、植被 BRG Draw Command `1`、GO Visible `8192/8192`。这里的 Draw Command 1 只指植被 BRG 命令，不等于整个 GameView 只有一个 Draw Call。

**稀疏大场地。** 总量 8192 株、1024 个 Heap。生成规则是 128 列 × 64 行；Z 方向名义跨度精确为 `(64-1) × 8 = 504` 米，X 方向用同一 504 米跨度分布，因此未加抖动的名义网格为 `504 × 504` 米。名义密度为 `8192 / (504 × 504) ≈ 0.03224994` 株/平方米，简写为 `≈0.03225`；它不是实际占地或地面面积密度。每个中心在 X/Z 还叠加最多 `±0.30` 米的确定性抖动，SceneAsset 实例中心实际范围约 `504.59 × 504.60` 米，地面边长为 `514` 米；显示网格间距 X `3.97` 米、Z `8.00` 米。XR Rig 可移动，Near/Far 为 `0.03/1000` 米，FOV（水平 × 垂直）约 `104.09° × 80°`，刷新率 90 Hz，Heap 加载/卸载范围 `150/175` 米，LOD Bias/Cull 为 `0.2/0.005`。设备三段没有保存姿态、Eye Buffer、质量档、光照配置和实际可见数；历史构建也不能与当前生成器建立源码级身份绑定。

编辑器默认姿态曾记录 Active Heaps `320/1024` → Frustum Candidates `2595` → Visible After LOD `520/8192`；该 520 不代表三段设备采样期间的实际可见数。

#### 三、两种 Box 代理准确代表什么

大尺寸 Box 与 15% 尺寸 Box 都是 24 顶点、12 三角形、36 索引。大尺寸 Box 的实际几何 Root Space AABB 与真实草相同；15% 尺寸 Box 的实际几何 AABB 为 `0.0473 × 0.0695 × 0.0546` 米，缩放后世界尺寸约 X `0.51–0.60` 米、Y `0.75–0.88` 米、Z `0.59–0.69` 米。最大旋转无关 XZ 外接圆直径为 `0.9105374` 米，小于 XZ 世界空间最小中心距 `1.01428664` 米，因此**静态低重叠 Box 在任意 Y 轴旋转下的水平包络**不相交；该门禁不含 Shader 风摆或其它运行时顶点位移。BRG 保守剔除 Bounds 仍保持真实草大小。

人工观察者在头显全景构图中记录两组 Box 的 8192 个实例全部进入画面，设备截图保存了该构图；三段未保存统一机器可见计数。头显观察与截图支持“全部入画”的观察结论，但不等价于程序化 `8192/8192` 可见计数。

高密度真实草到大尺寸 Box 的实验设计复用同一场景、SceneAsset、8192 个实例及其布局、材质链、LOD 参考、光照模式、场景 SH、相机和质量档，只替换 Prototype Mesh；但历史真实草构建缺少可核对的布局与光照签名，因此跨构建比较不是严格可复算的单变量实验。替换本身还同时改变网格拓扑、草叶轮廓、Alpha Clip 覆盖和内部 Overdraw，不能叫作“只改变顶点数”。

大尺寸 Box 到 15% Box 的约束更强：生成逻辑围绕原 Bounds 中心把顶点三轴缩到 15%，保留 UV、法线、切线、索引、SubMesh、材质、实例布局与逐株光照，并恢复大 Box 的保守剔除 Bounds；两个构建摘要的光照签名一致，15% 摘要还保存了实例布局签名。但它们仍是不同 APK、不同采样时段。两个 APK 的体积分别为 `270621866` 与 `186428728` 字节，相差 `84193138` 字节，即相对大尺寸 Box APK 减少 `31.111%`，这一跨构建漂移没有被解释，故：

- 各自测试构建内的 BRG→GO→BRG 顺序窗口可按各自会话证据使用；
- 跨真实草、大 Box、15% Box 的比较只作为相关性证据；
- 不能把跨包差异称为严格单变量证明。

三段会话连续性也不能统一处理：15% Box 保存了同一目标 PID；大 Box 与高密度真实草具有同一应用会话说明和连续时间窗，但没有 PID；稀疏组只有顺序时间窗、状态截图和操作者切换说明，没有明确同会话或同 PID 字段。四组都缺少自动化模式切换事件日志。几何变体之间则明确是三个独立 APK，不是一个进程里切换 Mesh。

#### 四、如何解释 CPU、GPU、Overdraw 与内存

**GPU。** 高密度真实草三段约 99% GPU 利用率与约 20 FPS 的组合，强烈支持该条件下 GPU 工作量是主要瓶颈。8192 株 × 704 三角形约为 576.7 万个实例三角形；双眼、Cull Off、Alpha Clip 和遮挡层叠还会继续增加工作量。现有跨构建对照只与“真实草几何与覆盖的组合成本重要”的判断一致，不能拆分顶点、三角形、Alpha Clip 与片元各自占比。

**CPU。** 大尺寸 Box 与 15% 尺寸 Box 中，普通 GO 的 CPU 利用率明显高于两段 BRG，且回切后恢复，支持普通 GO 完整路径的 CPU 侧总压力更高。没有主线程、渲染线程、Renderer、LOD、动态探针绑定和 Draw 提交分项，不能把差值唯一归因于其中一个环节。

**Overdraw。** Alpha Clip 植被通常在不透明队列绘制，所以会出现在 Opaque Overdraw 视图中；Transparent Overdraw 没有颜色不代表没有重复片元成本。Cull Off、草叶交叉、密集实例、较大屏幕尺寸和双眼都会增加工作量。即使本实验中的 BRG 路径减少了植被提交命令，也不会自动减少已经进入视野的几何或片元成本。

**Stale。** 这是 VrApi 报告字段，本记录按“合成器在应用未及时提交新帧时复用旧帧”的常见含义解释；它不是植被光照缓存过期。高密度真实草约 72 Stale/s 与约 20 FPS 一起表明应用明显跟不上 90 Hz。

**内存。** Total PSS 是 Android `dumpsys meminfo` 的整个应用进程分摊内存，原始单位 KB。普通 GO 段相对初始 BRG 分别增加约 `75.473 / 45.568 / 66.998 / 40.193 MiB`（稀疏、真实草、大 Box、15% Box）；这些值由 KB 差值除以 1024 得到。PSS 包含 Unity、XR、代码、纹理、图形资源与分配器保留，不能全部归因于 GameObject，也不能仅凭回切残留判断泄漏。

#### 五、BRG、普通 GO 与 SH 的实际差异

四组性能 APK 中：

- **BRG** 使用 `StaticLightColor`。刷新阶段在每株 `VisualRootSpaceBounds.center` 取得完整 L2 探针，以实例局部向上方向求出最终 RGB，并写入 SceneAsset/Heap；运行时直接读取最终颜色。
- **普通 GO** 从同一 SceneAsset 的实例变换展开 GameObject、Transform、MeshRenderer 与 LODGroup，材质启用 Unity GPU Instancing；Unity BlendProbes 按位置取得探针。Bakery 的非 Lightmap Shader 路径消费 `unity_SHAr/Ag/Ab` 的 L0/L1 表示，并按顶点法线执行 Geomerics 重建。

稀疏组的设备材料直接记录了上述 BRG/GO 光照代码路径；但该组没有保存场景灯、探针布置、Eye Buffer、质量档等配置，所以不能把其画面或性能差异进一步归因到具体光照配置。

因此，“探针烘焙模式为 Bakery L2”不等于两条运行时路径都在 GPU 上完整评估 L2。BRG 的完整 L2 已在刷新阶段求成最终 RGB；普通 GO 运行时使用 Ar/Ag/Ab 表示。两侧颜色和运行成本都不是严格等价。

#### 六、当前实现与历史设备数据的边界

当前 BRG 已改用新的逐株 ABI、光照记录和运行时组织，历史性能 APK 则使用旧版逐株最终颜色路径。两者不是同一协议，`StaticBakerySh` 也没有进入这四组设备实验。当前光照生成与消费见[Bakery L2 静态光照与投影代理](./unity-vegetation-bakery-static-lighting-pipeline.md)，逐株记录见[BRG 逐株 Buffer 的 32 字节压缩与量化 ABI](./unity-brg-packed-instance-buffer-quantization.md)。

因此，旧 APK 的 FPS、PSS、CPU/GPU 利用率只能描述本文冻结的历史系统；Editor 中的 Buffer 字节变化也不能替代当前实现的 Quest Vulkan 帧时、带宽、ALU、物理显存、功耗或热稳定性 A/B。

#### 七、当前实现的重测协议

要把历史趋势升级为当前结论，应在同一 APK 中完成自动化 A/B/A，并冻结下列条件：

1. **同一输入。** 固定设备系统、刷新率、质量档、Eye Buffer、场景、实例布局、Mesh、Material、LOD、灯光、Probe 和相机轨迹；保存对应内容摘要。
2. **同一会话。** 自动记录 PID、构建标识、模式切换事件、预热区间、采样起止、CPU/GPU 档位、频率、温度和电量；A、B、回切 A 使用同一进程。
3. **同一可见工作量。** 每个采样窗口记录 Active 区域、Frustum Candidates、Visible After LOD、三角形/顶点、Draw Command 和实际屏幕覆盖；不能用 Editor 默认姿态代替设备计数。
4. **区分两类问题。** “完整 BRG 系统对普通 GO 系统”保留各自真实光照和对象生命周期；“只比较提交路径”则必须让几何、材质、光照计算、剔除结果和可见实例完全相同，并通过冻结截图或预先定义的图像、实例与光照误差阈值确认功能等价。两类结果不能混写。
5. **同包切换几何。** 几何或覆盖实验应在同一包、同一场景中切换已冻结 Mesh，避免 APK 体积、资源剥离和采样时段成为跨包混杂。
6. **保存可分解指标。** 除 VrApi 窗口值外，记录原始字段名、字段单位、CPU 百分比归一化定义、窗口聚合方法，以及主线程、渲染线程、GPU Frame Time、Overdraw、PSS 分类和原始逐样本序列。
7. **平衡顺序并重复。** 预先规定冷却、预热、稳态判定、异常值、置信区间与效应量口径；跨会话重复多轮，并交替执行 A/B/A 与 B/A/B，报告顺序效应和回切恢复程度。

只有上述协议中的一个变量组发生预先声明的变化，才能把差异提升为对应机制的因果证据；否则仍应按完整系统相关性解释。

#### 八、适用边界

- **设备与场景**：数值只代表 Quest 3S 及本文列出的模型、场地、相机、刷新率、密度和历史光照条件；稀疏组缺少设备可见数及部分配置。
- **可见性**：Box 的“全部入画”来自头显观察和截图，不是程序化机器计数；15% Box 的不交叠门禁不含 Shader 顶点位移。
- **会话**：只有 15% Box 留有同 PID；其它组的连续性证据较弱，且头显姿态与预热时长未程序化锁定。
- **跨包**：大 Box 与 15% Box 存在 31.111% APK 体积漂移，跨几何变体只能作相关性证据。
- **路径差异**：BRG 与普通 GO 的光照和对象生命周期不同，本文是完整系统路径对比；CPU 利用率也没有线程或子系统分项。
- **时代边界**：这些历史实机数据不验证当前 ABI、Shader、光照布局或运行时组织，必须按第七节重新采集。
