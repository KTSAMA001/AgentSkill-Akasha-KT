# VitePress 文档站的程序构建与增量内容发布分离

**收录日期**：2026-08-23

**可信度**：⭐⭐⭐⭐（实地部署、自动化测试与生产回归）
**适用版本**：VitePress 1.6.x、Node.js 18+、Linux systemd/cgroup v1 或 v2

### 概要

小内存服务器上的 Markdown 文档更新不应触发前端程序、路由和全文搜索的整站 VitePress 构建。根本做法是把“程序发布”和“内容发布”拆成两条链路：程序在本地或 CI 构建为不可变产物，服务器只对变化的 Markdown、资源和轻量索引做有界增量处理，再通过候选隔离和原子指针发布。

### 内容

#### 问题不是 Markdown 转 HTML 本身

旧链路收到文档 Push 后直接执行整站 VitePress 构建。即使只改一篇记录，也会重新枚举路由、建立模块图、执行 SSR、打包浏览器程序并重建全局搜索数据。实践中，约 2 GB 内存的主机即使增加 swap，重复整站构建仍可能被 OOM Kill；如果构建前清空线上输出目录，失败还会直接造成网站不可访问。

因此必须区分两种工作：

- **程序构建**：Vue、Vite、VitePress、浏览器 JavaScript、CSS、页面模板和内容工作器发生变化。
- **内容编译**：Markdown、配套资源、索引元数据发生变化，需要更新可预览内容。

前者只应在资源充足且可复现的本地环境或 CI 中执行；后者可以留在服务器，但必须是增量、可回滚且有资源上限的任务。

#### 两条互不依赖的发布链路

```text
程序变化
  -> 本地或 CI 构建
  -> 生成文件清单与 SHA-256
  -> 上传不可变程序包
  -> 隔离候选验证
  -> 原子切换程序指针

内容变化
  -> 校验 Webhook HMAC、仓库与分支
  -> 收敛到 canonical main HEAD
  -> 对比上一内容 manifest
  -> 编译新增/变化文档，移除已删除文档
  -> 增量更新资源、搜索和统计投影
  -> 隔离候选验证
  -> 原子切换内容指针
```

服务器内容任务必须显式禁止 `npm install`、`vite build` 和 `vitepress build`。程序仓库的 Push 只能提示外部发布新程序包，不能在生产主机上自举更新和构建自身。

GitHub Delivery 只应作为“有新状态需要检查”的唤醒信号，不能作为顺序权威。工作器每次都拉取并验证 canonical 主分支 HEAD，避免延迟到达的旧事件让内容回退。

#### 内容领域层与表现层分离

浏览器不能天然显示 Markdown；所谓“浏览器直接使用 MD”仍需要在客户端下载解析器、代码高亮、公式和图表运行时，会改变首屏、无 JavaScript 正文、SEO、分享预览和低端设备负担。更稳妥的契约同时保留：

- 标准化 Markdown，供编辑器、轻量预览器或未来前端自行处理；
- 与具体 CSS/组件无关的语义 HTML，供默认前端直接首屏显示；
- 标题、元数据、目录、资源引用、搜索投影、源 revision、摘要和 Git 最后修改时间；
- 中立的 `data-*` 语义标记，不把当前前端类名或图标地址写入内容层。

表现适配器只消费已发布契约，负责页面壳、导航、主题、CSS、Mermaid 客户端增强和交互。这样可以保留当前界面的 URL 和体验，也可以增加其他前端，而不用复制 Markdown 同步、标签解释和搜索规则。

#### 增量编译的判定契约

上一版本 manifest 必须记录每篇文档、资源和全局依赖的指纹。下一次发布按以下规则处理：

- 新增或摘要变化的 Markdown：读取、解析并编译该文档。
- Git 能证明未变化且索引摘要一致的 Markdown：复用上一不可变产物，不读取正文。
- 删除的 Markdown：只从候选版本的文档、页面、搜索和目录中移除。
- 变化的资源：重新散列并复制；未变化资源复用。
- 仅表现模板、CSS 或浏览器程序变化：重新投影页面，不重新转换 Markdown。
- 内容 Schema、normalizer、编译器语义或全局元数据契约变化：有意全量失效，因为所有文档语义都可能改变。

搜索索引可以按稳定文档 ID 执行 add/replace/remove；即使最终 JSON 整体重写，也不应重新解析未变化的 Markdown。标签和统计可以从轻量 catalog 聚合。这里的“增量”指昂贵内容工作按变化量增长，不要求每个小型聚合文件都做字节级局部写入。

#### 候选隔离、原子发布与回滚

每个内容版本先写入独立暂存目录。旧文件可以用硬链接复用，但更新必须采用临时文件加重命名，避免修改旧版本共享 inode。只有 manifest、页面、API、资源和健康检查全部通过，才移动 `current` 一类的原子指针。

程序候选必须使用独立内容发布根和独立端口验证，不能提前移动生产内容指针。候选与生产可以共享同一个只读源 checkout，但必须用同一把同步锁串行访问。切换前同时记录程序和内容指针；生产收敛失败时，两者一起恢复。

不要把新版本直接构建到线上目录，也不要在构建开始前删除当前产物。失败候选应该保留足够诊断证据，但不能成为活动版本。

#### 内存边界必须由操作系统证明

只设置 Node.js `--max-old-space-size` 不能限制原生内存、代码页、缓冲区和子进程，因此还需要独立进程级硬边界。一个经实践验证的基线是：

- 文档默认分批处理，避免一次加载所有高亮语言和 Markdown；
- Node.js old-space 设独立上限；
- 用 `systemd-run` 和 cgroup 设置总内存上限、运行超时和失败回收；
- cgroup v2 同时核验 `memory.max` 与 `memory.swap.max=0`；
- cgroup v1 将 `memory.swappiness` 设为 0，并令 `memory.memsw.limit_in_bytes` 等于内存上限，然后回读确认。

cgroup v1 的做法可以抑制限额回收换页并阻止 swap 提供额外分配额度，但不能宣称完全阻止内核全局回收时换页。边界无法写入或回读不一致时，工作器应拒绝启动，而不是无界降级执行。

#### Webhook 和队列边界

- 使用原始请求体校验 GitHub `X-Hub-Signature-256` HMAC。
- 只允许明确的内容仓库、主分支和可发布路径。
- 手动重建端点必须使用独立令牌，不能把反向代理后的 `127.0.0.1` 当作真实客户端身份。
- 队列期望状态要原子持久化；进程重启、短暂失败或多个 Push 合并后，仍应收敛到最新 canonical HEAD。
- 健康接口应明确暴露 `serverBuildsEnabled=false`、当前任务、待处理目标和最近结果，但不能泄露内部路径或错误详情。

#### 验证必须覆盖真实目的

完整门控至少包含：

1. 内容单元测试：元数据、链接、标题锚点、契约校验。
2. 增量集成测试：新增、单篇修改、删除、资源变化、全局失效和零变化。
3. 发布事务测试：候选隔离、锁竞争、晚期失败、双指针回滚、损坏产物拒绝复用。
4. 安全测试：HMAC、仓库/分支白名单、手动令牌、公开健康信息边界。
5. 可复现程序包：精确文件清单、SHA-256、相同输入得到相同发布 ID。
6. 生产资源测试：目标 Node/systemd/cgroup 环境中的峰值 RSS 和 OOM 记录。
7. 浏览器验收：直接 URL、搜索、主题、目录、复制、公式、Mermaid、图片、移动端和无 JavaScript 正文。
8. 独立测试真实性审查：检查弱断言、错误 selector、错误渲染器假设、模拟投递冒充真实平台投递等假通过。

HTTP 200、构建退出码为 0、健康接口布尔值或签名模拟 Push 都不能单独证明完成。模拟 Push 可以证明 HMAC 到队列和工作器的处理链，但不能写成“GitHub 平台真实投递已经端到端验证”。测试脚本误判、源 Markdown 内容错误和公网链路问题也必须分开归因。

#### 一次迁移的量化边界

一次约 200 篇文档的冷迁移在目标小内存主机上约 9 秒完成，峰值 RSS 约 212 MiB，低于 640 MiB 工作器硬边界；同 revision 再次触发约 1.7 秒收敛到 `already-current`。隔离集成测试证明单篇修改只读取、编译该篇，未变化文档复用。

这些数字只能作为同技术栈和相近内容规模的容量参考，不是普遍性能承诺。冷迁移全量处理是 Schema/表现契约变化导致的有意失效，不等于增量失效；生产环境第一次真实单篇内容更新后，仍应核对 `compiled`、`readDocuments` 和资源散列计数。
