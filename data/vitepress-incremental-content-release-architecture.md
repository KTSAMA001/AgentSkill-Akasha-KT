### 概要

一篇 Markdown 发生变化，却让小内存服务器重新生成所有路由、页面、搜索数据和前端程序，最终因内存不足而中断——这不是 Markdown 转 HTML 太重，而是内容更新误触发了整站程序构建。

本记录说明如何把原本以 VitePress 整站构建为中心的文档站，迁移为“程序离线构建、内容在服务器增量发布”的架构。它不是 VitePress 原生的单页增量构建功能，而是一套独立内容平台：保留静态 HTML、原有 URL、首屏和搜索体验，同时让新增或修改文档的处理成本主要随变化量增长。

### 内容

#### 事故背景：改一篇文档，为什么会拖垮整站

典型的 VitePress 站点把以下工作放在同一次构建中：

- 读取和解析全部 Markdown；
- 生成全部页面路由与静态 HTML；
- 执行服务端渲染（SSR，即在构建阶段先生成浏览器可直接读取的 HTML）；
- 打包 Vue、主题、CSS 和浏览器 JavaScript；
- 重建全文搜索索引与全局统计。

这套方式简单可靠，适合在本地或 CI 中完整构建。但如果 GitHub 每次出现文档 Push，生产服务器就直接执行整站构建，那么只改一篇记录也会重复上述全部工作。

实践中的服务器只有约 2 GB 内存。构建进程多次触及内存上限并被 Linux 终止，也就是常说的 OOM Kill（Out Of Memory，内存耗尽）。增加 swap（磁盘交换空间）只能推迟压力，并不能让任务变得有界。如果脚本还在构建前清空线上目录，一次失败就可能把“构建失败”扩大为“网站不可访问”。

这次改造希望同时满足四个目标：

1. 文档提交到 GitHub 后，网站仍能自动出现新内容。
2. 修改一篇文档时，不重新构建整个前端程序，也不重新解析其他 Markdown。
3. 新版本失败时，读者始终看到完整旧版，而不是半成品或空目录。
4. 当前界面和 URL 保持不变，同时允许未来增加另一套前端表现。

#### 先给结论：分离的是发布责任，不是让两边毫无关系

系统需要把“程序变化”和“内容变化”分开处理：

| 变化类型 | 包含什么 | 在哪里构建 | 服务器做什么 |
|---|---|---|---|
| 程序发布 | 页面模板、主题、CSS、浏览器 JavaScript、内容工作器 | 本地或 CI | 校验并激活程序包；必要时从已有内容对象重绘页面候选，但不重新解析 Markdown |
| 内容发布 | Markdown、图片等资源、目录、搜索和统计数据 | 服务器的受限工作器 | 只读取并编译发生变化的内容 |

两条链路拥有不同的触发条件和发布节奏，但并非“互不依赖”。程序必须知道自己支持哪一版内容数据格式；内容页面也必须引用与它匹配的程序资源。两边通过一个带版本号的**内容契约**保持兼容。

这里的内容契约可以理解为程序和内容之间共同遵守的装箱单：字段叫什么、哪些字段必需、HTML 中允许出现哪些中立标记，都由它定义。只要契约兼容，内容规则和前端外观就可以分别演进。

这也意味着 VitePress 不再参与生产服务器上的文档编译。现有界面由一套**表现适配器**复现，也就是“把中立内容套入当前网站主题”的前端层；Vite/Vue 仍可用于在本地构建浏览器程序，但不能把这套方案误解成 VitePress 自带了“只构建一篇页面”的能力。

#### 一次页面访问究竟经过什么

先看读者打开 `/records/example` 时发生的事情：

```text
浏览器请求 /records/example
          │
          ▼
Nginx 在当前内容版本中找到 records/example.html
          │
          ├─ HTML 已包含标题、正文、目录和元数据
          │
          └─ HTML 引用某个确定程序版本的 CSS / JavaScript
                         │
                         ▼
              浏览器添加搜索、主题、复制、Mermaid 等交互
```

服务器在每次访问时不会临时解析 Markdown，也不会运行一个应用进程拼装正文。Nginx 直接返回已经生成好的静态 HTML。即使浏览器禁用 JavaScript，文章正文仍然存在；JavaScript 只负责交互增强。

一个简化后的部署目录如下：

```text
site-root/
├── runtime/
│   ├── releases/program-a/        # 不可修改的程序版本
│   └── current -> releases/program-a
└── content/
    ├── releases/content-b/        # 不可修改的内容版本
    │   ├── index.html
    │   ├── records/example.html
    │   ├── content/documents/example.json
    │   ├── content/search/index.json
    │   └── manifest.json
    └── current -> releases/content-b
```

`runtime/current` 指向当前程序版本，`content/current` 指向当前内容版本。Nginx 的站点根目录是 `content/current`，并把无扩展名 URL `/records/example` 映射到 `records/example.html`，因此新增文档不需要重新运行 VitePress 路由生成器。另一个 Nginx 映射把 `/app/releases/<program-id>/` 指向 `runtime/releases/<program-id>/` 中的浏览器资源；`runtime/current` 主要供工作器和少量兼容入口确定当前程序，内容页面优先引用不可变的版本 URL。

内容页面中的 CSS 和 JavaScript 使用带版本号的不可变 URL，例如 `/app/releases/program-a/...`。这样即使新程序正在发布，旧内容仍能加载自己匹配的旧程序资源，不会出现 HTML 已切换、脚本还未切换的混合状态。

这里还要区分“单个文件请求完整”和“同一页面的多次请求属于同一版本”。切换 `content/current` 可以保证 Nginx 的一次文件查找落在完整旧目录或完整新目录，但旧 HTML 如果随后访问未带版本号的 `/content/search/index.json` 或 `/assets/example.png`，指针可能已经切换，它就可能读到新版内容资源。若业务要求整个浏览器会话保持同一内容快照，搜索、图片和内容 JSON 也必须使用 `/content/releases/content-b/...` 这样的版本化 URL，或使用由内容摘要命名的地址；旧内容版本要保留到缓存和活跃请求的安全窗口结束。

#### 内容包里为什么同时保留 Markdown 和语义 HTML

浏览器不能天然显示 Markdown。“直接把 MD 发给浏览器”仍然需要把 Markdown 解析器、代码高亮、公式和图表运行时交给每位读者下载和执行，也会改变首屏速度、无 JavaScript 阅读、搜索引擎抓取和分享预览。

更稳妥的做法是让每篇文档生成一份与具体界面无关的数据对象。下面是删减后的内容契约示例：

```json
{
  "schemaVersion": "document.v2",
  "id": "example",
  "canonicalPath": "/records/example",
  "source": {
    "revision": "git-commit",
    "sha256": "source-hash",
    "lastModifiedAt": "2026-08-23T06:30:00Z"
  },
  "metadata": {
    "title": "示例文章",
    "tags": ["web"]
  },
  "content": {
    "markdown": "标准化后的 Markdown",
    "semanticHtml": "与主题无关的语义 HTML"
  },
  "outline": [],
  "assets": [],
  "search": {}
}
```

其中：

- Markdown 供编辑器、其他预览器或未来前端使用；
- 语义 HTML 供默认网站直接生成静态页面；
- 元数据、目录、资源和搜索字段由所有前端共享；
- Git 提交号和摘要用于追踪来源、判定变化与回滚；
- `data-*` 一类中立标记表达“这是图表”“这是元数据”，但不写入某个主题专属的 CSS 类或图标地址。

**表现适配器**就是把这份中立数据套入某一套网站外观的前端层。它负责页面壳、导航、主题、CSS、搜索交互和 Mermaid 等客户端增强，但不重新解释标签规则，也不读取源知识库。

搜索条目、统计数据、标签目录和最终静态页面都属于**派生结果**，也常被称为投影：它们从同一份内容契约产生，损坏时可以重建，不应成为另一份互相冲突的权威数据。

#### manifest 如何决定“这次只处理什么”

每个内容版本都保存一份 `manifest.json`。manifest 可以理解为该版本的**发布账本**：它记录源提交、编译规则版本、表现版本，以及每篇文档和资源的摘要与产物路径。

一个最小账本大致如下：

```json
{
  "contentReleaseId": "content-b",
  "programId": "program-a",
  "sourceRevision": "git-commit",
  "contractVersion": "document.v2",
  "contentFingerprint": "content-rules-hash",
  "projectionFingerprint": "search-and-catalog-rules-hash",
  "presentationFingerprint": "presentation-rules-hash",
  "documents": {
    "example": {
      "inputHash": "source-plus-metadata-hash",
      "documentPath": "content/documents/example.json",
      "pagePath": "records/example.html"
    }
  }
}
```

下一次发布把新输入和上一份账本比较：

其中 `contentReleaseId` 标识不可变内容快照，`programId` 标识页面必须加载的不可变程序版本，`contractVersion` 用来判断两者是否兼容。回滚时应恢复这个已经验证的组合，而不是临时猜测两个“当前版本”能否搭配。

| 发生的变化 | 应执行的工作 |
|---|---|
| 新增或修改一篇 Markdown | 读取、编译并重新生成该篇页面 |
| 删除一篇 Markdown | 从候选版本的页面、目录和搜索中删除该篇 |
| 修改图片等资源 | 只重新散列并复制变化资源 |
| 修改某篇索引元数据 | 只让受影响文档和派生数据失效 |
| 修改搜索或统计规则 | 重建轻量派生数据，不重新解析 Markdown |
| 修改页面模板或主题 | 从已有内容契约重新生成页面，不重新读取 Markdown |
| 修改内容字段、Markdown 编译规则或全局语义 | 有意重新编译全部文档 |
| 同一提交重复通知 | 验证当前版本后直接结束 |

“增量”不等于每个输出文件都只能修改几个字节。搜索索引最终可能仍是一个整体 JSON 文件，但更新它不需要重新解析 200 篇 Markdown。真正要控制的是昂贵工作是否随变化文档数量增长。

#### 新版本如何在不影响读者的情况下上线

最基本的发布事务只有四步：

1. **生成候选版本**：把新结果写入一个与线上版本隔离的目录。候选版本是“已经完整生成、但尚未对读者生效”的版本。
2. **验证候选版本**：检查账本、页面、静态内容 JSON/API、资源、搜索以及程序兼容性。
3. **原子切换入口**：一次性把 `content/current` 指向新版本。这里的“原子”首先表示单个文件请求只能落在完整旧目录或完整新目录，不会看到尚未生成完的候选；实现通常是在同一文件系统内原子重命名符号链接或很小的指针文件。
4. **保留旧版回滚**：新版本出现问题时，把指针切回已验证的旧目录。

实现时可以用硬链接复用未变化文件，减少磁盘复制；更新文件必须先写临时文件再重命名，避免修改旧版本共享的底层文件。原子重命名还要求候选和指针位于同一文件系统；旧版本不能在切换后立刻删除，要给正在读取它的请求和缓存留出安全窗口。硬链接和 inode（文件系统用于标识底层文件的编号）只是优化细节，不是理解本架构的前提。

程序与内容可以各有一个运维用的当前指针，但两个指针的先后替换并不会自动组成跨请求的原子事务。更强的发布协议是：先放好不可变程序和内容资源，让内容账本绑定兼容的 `programId`，使 HTML 中所有关键资源都引用确定版本，最后只切换 `content/current` 这个读者入口。`runtime/current` 可以供工作器和兼容入口使用，但正文页面不能依赖它选择关键程序资源。回滚时切回旧内容入口，旧账本会重新绑定已保留的旧程序版本。

候选进程和生产进程还可能共享同一个 Git 工作目录。内容编译器不会改写知识文档，但 `git fetch` 和 `git checkout` 会改变工作目录当前指向的提交，因此这些动作必须由同一把同步锁串行执行。锁保护的是 Git 状态切换，不是把 Markdown 当作可写数据。

#### Webhook 是门铃，不是事实来源

GitHub Webhook 只是通知服务器“仓库可能有新状态”。通知可能延迟、重复或乱序，所以不能按到达顺序直接发布其中声称的提交。

工作器收到通知后，应重新拉取远端主分支，并把远端主分支最新提交作为唯一目标。英文文档常把它称为 canonical main HEAD，这里就是“服务器亲自确认的主分支最新提交”。即使旧通知晚到，工作器也只会继续收敛到最新状态，不会回退。

公开 Webhook 还必须解决伪造请求问题。HMAC 可以理解为发送方和接收方用共享密钥算出的请求指纹；服务器用原始请求体重新计算并比较 GitHub 的 `X-Hub-Signature-256`，确认通知没有被冒充或篡改。密钥只能留在服务器端。

此外还应做到：

- 只接受明确的内容仓库、主分支和可发布路径；
- 手动重建入口使用独立令牌，不能因为反向代理显示来源是本机地址就默认可信；
- 把待处理目标原子写入磁盘，服务重启后继续处理；
- 合并短时间内的多次通知，最终只发布最新主分支状态；
- 明确禁止服务器执行 `npm install`、`vite build` 或 `vitepress build`。

#### 内存限制为什么需要两层

Node.js 的 `--max-old-space-size` 只限制 JavaScript 主要堆区，不能覆盖原生库、代码页、文件缓冲区或子进程。因此资源边界至少要有两层：

1. 内容工作器分批读取文档，并限制 Node.js 堆大小；
2. Linux 使用 cgroup 给整个工作器进程组设置总内存和运行时间上限。

cgroup 是 Linux 用来限制一组进程资源的机制。cgroup v2 可以同时核验内存上限和 `memory.swap.max=0`，明确禁止该工作器使用 swap。旧版 cgroup v1 没有完全等价的开关，只能把 `memory.swappiness` 设为 0，并让“内存加 swap”的总额度等于内存上限。

cgroup v1 的做法可以防止 swap 给任务增加额外分配空间，并抑制该组进程在达到限额时换页，但不能承诺内核进行全局内存回收时绝不换页。任何限制无法设置或回读不一致时，工作器都应拒绝启动，而不是悄悄无界运行。

#### 从现有 VitePress 站迁移的顺序

不需要第一天就删除旧站。更安全的迁移顺序是：

1. **盘点全局依赖**：列出哪些 Markdown 规则、插件、标签、搜索和页面依赖全站状态。
2. **定义内容契约**：先固定文档 ID、URL、元数据、Markdown、语义 HTML、目录和资源格式。
3. **生成全量基线**：用新内容平台完整生成一次站点，与旧 VitePress 输出逐页对照。
4. **实现当前表现适配器**：复现现有主题、搜索和交互，确认读者体验没有变化。
5. **加入发布账本和增量判定**：覆盖新增、修改、删除、资源变化、规则变化与重复通知。
6. **加入候选目录和原子切换**：演练编译失败、切换失败和回滚，证明旧版始终可访问。
7. **接入签名 Webhook 和持久队列**：先影子运行，不移动生产指针，观察它是否总能追上主分支。
8. **在目标服务器测量资源**：记录峰值总内存，而不只看 Node.js 堆；验证超限时旧站仍然存在。
9. **切换 Nginx 到新内容指针**：完成直接 URL、搜索、主题、代码、公式、图表、图片和移动端浏览器回归。
10. **关闭服务器整站构建**：只有真实 GitHub 提交、候选验证和回滚演练都通过后，才删除旧自动构建入口。

如果切换后发现新链路不能稳定跟上主分支，应把 Nginx 指回旧版静态目录并恢复旧 Webhook，而不是在新链路上边运行边修复。回滚能力必须在切换前存在。

#### 哪些站点值得这样做

这套架构适合：

- 文档数量较多或增长持续；
- 内容更新频繁，但网站程序变化较少；
- 生产服务器资源有限；
- 必须保留静态 HTML、直接 URL、SEO 和无 JavaScript 正文；
- 计划让同一份内容支持不同前端。

它不一定适合：

- 只有少量页面、很少更新的小站；
- 已经能在 CI 中快速完成整站构建并原子发布到 CDN；
- 强依赖大量 VitePress 构建期插件，而且没有精力重现其语义；
- 团队不愿维护自定义内容契约、搜索投影、发布账本和回滚流程。

这套方案节省的是生产服务器的重复计算和事故风险，代价是需要自己维护内容编译器、版本兼容、搜索数据与更多发布测试。若 CI 全量构建已经足够快且可靠，把完整静态产物从 CI 原子部署到服务器通常更简单。

#### 怎样证明“增量”不是一句口号

至少要分别验证：

- 单篇新增、修改和删除是否只读取预期文档；
- 规则变化是否会正确触发必要的全量失效；
- 候选失败和切换失败是否保持旧指针不变；
- 程序变化能否只从已有内容契约重绘页面，而不读取源 Markdown；
- 目标服务器的总内存峰值是否低于硬边界；
- 真实浏览器中的 URL、正文、搜索、主题、公式、Mermaid、图片和移动端是否保持一致；
- 真实 GitHub 提交是否经过 Webhook、队列和工作器自动到达线上。

HTTP 200、构建退出码为 0、健康接口中的一个布尔值或签名模拟请求，都不能单独证明这些目标。模拟请求能验证“验签到工作器”的处理链，但只有真实 GitHub 提交才能覆盖平台投递这一步。测试脚本误判、源 Markdown 自身错误和公网链路问题也要分开归因。

#### 实测结果与证据边界

一次约 200 篇文档的冷迁移在目标小内存主机上约 9 秒完成，进程驻留内存峰值（RSS）约 212 MiB，低于 640 MiB 工作器硬边界。同一 Git 提交再次通知时，约 1.7 秒确认无需更新。

随后一次真实 GitHub 提交同时新增或修改了 3 篇记录。生产报告显示只读取、编译和生成了这 3 篇页面，其余 206 篇复用，没有重新散列无关资源；任务约 1.25 秒完成，峰值约 180 MiB。这次结果覆盖了 GitHub 平台投递、Webhook、队列、主分支确认、增量工作器和线上静态页面。

这些是案例报告数据：文档规模按发布账本中的记录数计算，峰值取工作器报告的进程驻留内存，不等同于整台主机的总内存。自动化测试覆盖候选失败、指针保持与回滚，真实生产提交覆盖平台投递和增量上线；没有为了取证而在生产环境主动制造 OOM。数字只能作为同技术栈和相近内容规模的容量参考，不是普遍性能承诺。第一次冷迁移需要全量处理，是内容格式和表现规则变化造成的有意失效，不代表增量机制无效。

#### 最后的采用检查

准备关闭服务器整站构建前，至少应能回答“是”：

- 程序是否已经能在服务器外构建，并以不可变产物部署？
- 内容契约是否有版本，程序是否会拒绝不兼容的内容？
- 单篇变化是否有报告证明只读取和编译该篇？
- 新版本是否总在候选目录完成验证后才切换？
- 程序和内容是否都能恢复到上一组兼容版本？
- 工作器是否有操作系统级内存边界，且边界失效时拒绝运行？
- 真实 GitHub 提交和真实浏览器是否都通过过验收？

如果其中任何一项还不能确认，就应保留旧链路或继续影子运行。根本目标不是追求“增量”这个标签，而是让内容更新的成本与变化量相称，并保证任何失败都不会破坏读者正在访问的版本。
